## Оприходование товара (`prihod` / `Income`) — текущая реализация

### 1. Модель данных

Документ оприходования — это запись в общей таблице `documents` с `doc_type = 'prihod'` (строка 63 `models.rs`):

```rust
#[serde(rename = "prihod")] Income,  // ПриходТовара
```

Структура документа (строки 89–102):
- `id`, `doc_type`, `doc_number`, `doc_date`, `posted`
- `warehouse_id` — склад, куда приходуется товар
- `counterparty_id` — поставщик
- `total_amount` — сумма документа
- Табличная часть: `document_lines` (товары: `product_id`, `quantity`, `price`, `cost_price`)
- Оплата: `document_payments` (тип оплаты, сумма)

### 2. API-эндпоинты (`main.rs`)

| Метод | Путь | Назначение |
|-------|------|------------|
| `POST` | `/api/documents` | Создать документ (любого типа, включая `prihod`) |
| `POST` | `/api/documents/:id/post` | Провести документ |
| `POST` | `/api/documents/:id/unpost` | Отменить проведение |

**Создание** (`create_document`, строки 116–166): принимает JSON с `doc_type: "prihod"`, `warehouse_id`, `counterparty_id`, массив `lines` (product_id, quantity, price, cost_price) и `payments`. Считает `total_amount` как сумму `quantity × price` по строкам. Вставляет в `documents`, `document_lines`, `document_payments` одной транзакцией.

### 3. Бизнес-логика проведения (`posting.rs`)

**`post_document()`** (строки 27–106) — основной метод:

1. **Блокирует** документ (`SELECT ... FOR UPDATE`)
2. Проверяет, что документ ещё **не проведён** (`AlreadyPosted`)
3. Загружает строки и платежи
4. **Генерирует движения** через `generate_movements()`
5. **Валидирует** через `validate_posting()`
6. **Записывает движения** в регистры (`write_movements`)
7. **Обновляет материализованные остатки** (`update_stock_balances`)
8. Помечает `posted = true`
9. Публикует событие `DocumentPosted` в event bus (для плагинов — фискального, аналитики)

**Для `DocType::Income` (строки 312–364) генерируются три вида движений:**

| Регистр | Направление | Что происходит |
|---------|-------------|----------------|
| `StockBalance` | **Income** | Товар приходуется на склад (`warehouse_id`) |
| `Settlement` | **Expense** | Возникает задолженность перед поставщиком (`counterparty_id`) |
| `Cash` | **Expense** | Расход денег (если указаны `payments`) |

Особенность: **валидация для `Income` отсутствует** — в `validate_posting()` (строка 640) для `DocType::Income` стоит `_ => {}`. Остатки не проверяются (в отличие от `Receipt` и `WriteOff`, где проверяется `InsufficientStock`).

### 4. Отмена проведения (`unpost_document`, строки 112–237)

Читает существующие движения из регистров → удаляет их → применяет **обратные** движения к `stock_balances`:
- `Income` → вычитает из остатка
- `Expense` → добавляет к остатку

### 5. Схема БД (миграция `001_core_schema.sql`)

Задействованные таблицы:
- `documents` — заголовок документа
- `document_lines` — строки товаров
- `document_payments` — строки оплаты
- `stock_movements` — движения по складу (регистр)
- `cash_movements` — движения по деньгам
- `settlement_movements` — движения по взаиморасчётам
- `stock_balances` — текущие остатки (материализованные)

### 6. Текущее состояние

**Что реализовано:**
- Полный цикл: создать → провести → отменить проведение
- Все три регистра движений (склад, деньги, взаиморасчёты)
- Материализованные остатки с `ON CONFLICT ... DO UPDATE`
- Поддержка `cost_price` (себестоимость) в строках
- Событийная модель — плагины получают `DocumentPosted`/`DocumentUnposted`

**Что не реализовано / потенциальные доработки:**
- Нет **валидации** при проведении `Income` (например, проверка обязательности склада/поставщика)
- Нет **автоматического расчёта себестоимости** (cost_price передаётся клиентом, не вычисляется по партиям)
- Нет **учёта НДС** в движениях (поле `vat_rate` есть в `products`, но не используется при проведении)
- Нет генерации **номера документа** (`doc_number` всегда `NULL`)
- Таблица `payment_operations` и `fiscal_operations` в схеме есть, но в `Income` не задействованы — они для чеков ККМ

## Как получить остатки «на момент»

Материализованный срез хранит только **текущий** итог. Чтобы получить остаток на **произвольную дату**, нужно считать из регистра:

```sql
SELECT
  product_id,
  warehouse_id,
  COALESCE(SUM(CASE WHEN direction = 'income'  THEN quantity END), 0)
  - COALESCE(SUM(CASE WHEN direction = 'expense' THEN quantity END), 0) AS quantity_as_of
FROM stock_movements
WHERE period <= '2026-05-10'  -- нужная дата
GROUP BY product_id, warehouse_id
```

Но это считает всё с нуля. Если есть seed-остатки (начальное сальдо), их надо добавить:

```sql
-- 1. Берём seed-сальдо как отправную точку
WITH seed AS (
  SELECT product_id, warehouse_id, quantity
  FROM stock_balances   -- seed-данные: это остатки на момент загрузки
  WHERE ...             -- отметка, что это начальное сальдо
)
-- 2. Суммируем все движения ПОСЛЕ seed до нужной даты
SELECT
  s.product_id, s.warehouse_id,
  s.quantity + COALESCE(
    SUM(CASE WHEN sm.direction = 'income'
      THEN sm.quantity ELSE -sm.quantity END), 0
  ) AS quantity_on_date
FROM seed s
LEFT JOIN stock_movements sm
  ON sm.product_id = s.product_id
  AND sm.warehouse_id = s.warehouse_id
  AND sm.period > '2026-05-10T00:00:00Z'  -- дата seed
  AND sm.period <= '2026-05-20T00:00:00Z' -- дата отчёта
GROUP BY s.product_id, s.warehouse_id, s.quantity
```

На практике это **тяжёлый запрос** — полный скан регистра по индексу `(product_id, period)`.

## Чем наша архитектура отличается от 1С

В 1С пересчёт **итогов по регистру** (месячных агрегатов) происходил **при каждом проведении документа**, затрагивающем регистр. Если в базе миллион документов, а проводится документ с датой на год назад — 1С пересчитывал итоги для ВСЕХ периодов, затронутых изменением. Чем больше документов — тем дольше каждое проведение. Деградация была **O(n) по числу документов в периоде**.

У нас в **PostgreSQL + Rust**:

| Операция | Сложность | От чего зависит |
|----------|-----------|-----------------|
| `post_document` (запись) | **O(1)** по всей БД | Только число строк в документе |
| `post_document` (валидация) | **O(k)** — k строк документа | `SELECT ... FOR UPDATE` по конкретному товару |
| `stock_balances` UPSERT | **O(1)** | UPSERT по PK — константа |
| `stock_movements` INSERT | **O(log n)** | B-tree вставка — логарифм, практически константа до 10⁸ |
| `unpost_document` | **O(k)** | DELETE по `document_id` (индекс) + UPDATE остатков |
| **Пересчёт `stock_balances` с нуля** | **O(n)** | Полный `GROUP BY` по `stock_movements` |

**Ключевое отличие**: проведение документа **никогда не зависит от размера всей БД**. Никаких «итогов по периоду», никакого пересчёта месячных срезов при записи.

## Скорость пересчёта — прикидка

Пересчёт `stock_balances` = один SQL:

```sql
INSERT INTO stock_balances
SELECT product_id, warehouse_id,
       SUM(CASE WHEN direction='income' THEN quantity ELSE -quantity END)
FROM stock_movements GROUP BY product_id, warehouse_id
```

Примерные цифры на PostgreSQL 16, 4 ГБ ОЗУ, SSD, средний сервер:

| Объём `stock_movements` | Временной бюджет |
|------------------------|-------------------|
| **10 000 строк** | ~20–50 ms |
| **100 000 строк** | ~80–200 ms |
| **1 000 000 строк** | ~300–800 ms |
| **10 000 000 строк** | ~2–5 секунд |
| **100 000 000 строк** | ~15–40 секунд |

Это **полный пересчёт с нуля**. Не десятки минут, как в 1С с «Расчёт итогов» для большого регистра, а секунды — потому что Rust-сервер не участвует, PostgreSQL делает весь `GROUP BY` в памяти или через HashAggregate.

## Когда деградация может проявиться

Сценарии, где скорость **может** упасть:

**1. `validate_posting` для `Receipt` (проверка остатков)**

Сейчас делает `SELECT quantity FROM stock_balances WHERE ... FOR UPDATE` — O(1), не проблема.

Если когда-нибудь понадобится валидация с расчётом себестоимости по FIFO — это будет `SELECT ... FROM stock_movements WHERE product_id = $1 AND period <= $2 ORDER BY period` — **O(m)** по числу движений товара. Для товара с миллионом движений — миллисекунды с SQL-курсором, секунды без него.

**2. Отчёт «Остатки на дату» через регистр (без снапшотов)**

Расчёт на лету `SUM(... WHERE period <= date) GROUP BY` — полный скан `stock_movements`. Для 10 млн строк — 1–3 секунды. Приемлемо для разового отчёта, не годится для дашборда на каждую секунду.

**3. `unpost_document` при хаотичном порядке**

Если регулярно отменять проведение документов из разных периодов — не страшно, O(k). Но если делать это в цикле для 10 000 документов — будет 10 000 отдельных транзакций. Пакетный `unpost_documents` решит.

## Где узкое место НЕ наступит

- **Рост числа товаров**: всё завязано на `product_id, warehouse_id` — сколько бы ни было товаров, UPSERT по PK константа
- **Рост числа документов**: `SELECT ... FOR UPDATE` по `documents` — точечный, PK
- **Перепроведение**: нет пересчёта «всех итогов по месяцу», только свои строки

## Резюме

| Аспект | 1С (классика) | PTM (Rust + PostgreSQL) |
|--------|---------------|------------------------|
| Проведение | O(n) — чем больше док-ов, тем дольше | O(k) — только строки документа |
| Пересчёт итогов | При каждом проведении | Только по запросу (ручной / крон) |
| Полный пересчёт | Минуты–часы | Секунды для 10 млн строк |
| Деградация за 5 лет | Заметна (итоги растут) | **Не заметна** |
| Снапшоты на дату | Встроенные (периоды) | Нужно добавить (опционально) |

Для магазина (~1000 операций/день, ~300 000 документов/год) — **деградации не будет ближайшие 5+ лет**. Если нужна будет производительность «отчёта на дату» на миллиарде движений — добавим партицирование `stock_movements` по месяцам + материализованные срезы. ## Как это устроено в 1С (для сравнения)

В 1С регистр накопления хранит **периодические итоги** — агрегированные остатки на **конец каждого месяца**. Когда запрашивают остатки на 15 марта, 1С:
1. Берёт итог на **конец февраля** — O(1), готовый агрегат
2. Досчитывает движения с **1 по 15 марта** — только движения одного периода

## Как это можно сделать у нас

Чтобы получить такой же механизм, нужна таблица срезов:

```sql
CREATE TABLE stock_balances_snapshot (
    period        DATE NOT NULL,            -- конец дня
    product_id    UUID NOT NULL,
    warehouse_id  UUID NOT NULL,
    quantity      NUMERIC(12,3) NOT NULL,
    PRIMARY KEY (period, product_id, warehouse_id)
);
```

Заполняется раз в день (кроном):

```sql
INSERT INTO stock_balances_snapshot (period, product_id, warehouse_id, quantity)
SELECT
    CURRENT_DATE,
    product_id,
    warehouse_id,
    quantity
FROM stock_balances;
```

Тогда остатки на дату считаются так:

```sql
-- Берём ближайший снапшот до даты
WITH snapshot AS (
    SELECT product_id, warehouse_id, quantity
    FROM stock_balances_snapshot
    WHERE period = (
        SELECT MAX(period) FROM stock_balances_snapshot
        WHERE period <= '2026-03-15'
    )
)
-- Досчитываем движения после снапшота до нужной даты
SELECT
    s.product_id,
    s.warehouse_id,
    s.quantity + COALESCE(SUM(
        CASE WHEN sm.direction = 'income' THEN sm.quantity
             WHEN sm.direction = 'expense' THEN -sm.quantity END
    ), 0) AS quantity_on_date
FROM snapshot s
LEFT JOIN stock_movements sm
    ON sm.product_id = s.product_id
    AND sm.warehouse_id = s.warehouse_id
    AND sm.period > (SELECT MAX(period) FROM stock_balances_snapshot WHERE period <= '2026-03-15')
    AND sm.period <= '2026-03-15T23:59:59Z'
GROUP BY s.product_id, s.warehouse_id, s.quantity;
```

Это **быстрее полного скана** во столько раз, сколько снапшотов в истории. Если снапшот ежедневный — читаем не всю историю (5 лет), а только движения за 1–2 дня.

## 2. Пересчёт при изменении данных задним числом

Сценарий: провели документ за январь, потом отменили его проведение и перепровели с другой суммой.

**Если снапшотов нет:** материализованный срез `stock_balances` корректируется точечно через `update_stock_balances()` при каждом `post`/`unpost`. Всё остаётся корректным автоматически.

**Если снапшоты есть:** снапшот — это замороженный срез на момент времени. При изменении задним числом **все снапшоты, начиная с даты изменения, устаревают**.

Пример:
- Документ от 15 января меняет количество товара
- Снапшот на **31 января** становится неверным
- Снапшот на **28 февраля** тоже неверен — в него вошли неверные данные
- Любой запрос с `as_of = март` будет считать так: `снапшот_февраля + движения_марта` — и получит неверную базу

**Решение:** при `unpost`/`post` документа удалять все снапшоты `WHERE period >= doc.doc_date`. Тогда запросы будут автоматически брать предыдущий верный снапшот и досчитывать движения после него + после изменения.

Удаление одного ряда снапшотов — `DELETE FROM stock_snapshots WHERE period >= '2026-01-15'` — быстрее пересчёта.

Можно пойти дальше: сделать автоматический **пересчёт снапшотов** при изменении документов через фоновую задачу, но для начала достаточно удаления — на производительность запросов это влияет по минимуму, потому что берётся предыдущий снапшот, который дальше от даты запроса, и досчитывается чуть больше движений.

## 3. Есть ли в PostgreSQL быстрая сумма по колонке?

Да, `SUM(column)` — это агрегатная функция, но она **всегда читает все строки**, которые попадают в `WHERE` + `GROUP BY`. Никакого «накопленного итога», который можно было бы достать за O(1), в PostgreSQL нет из коробки.

Однако есть несколько трюков:

**А. `COUNT(*)` по регистру (быстрый)**

`SELECT count(*) FROM stock_movements` использует **Index Only Scan** по любому индексу — работает за миллисекунды для любого объёма. Это количество строк, не сумма.

**Б. Материализованные представления**

```sql
CREATE MATERIALIZED VIEW mv_stock_totals AS
SELECT product_id, warehouse_id,
       SUM(CASE WHEN direction='income' THEN quantity ELSE -quantity END) AS total
FROM stock_movements
GROUP BY product_id, warehouse_id;
```

`REFRESH MATERIALIZED VIEW` — полный пересчёт, но чтение — O(1) по PK. Быстрое чтение, медленная запись.

**В. **`stock_balances` — это и есть такой MV**, только обновляется инкрементально, а не полным пересчётом.

**Г. **Оконные функции для «накопленного остатка»**

Если нужен график изменения остатка товара во времени:

```sql
SELECT period,
       SUM(CASE WHEN direction='income' THEN quantity ELSE -quantity END)
        OVER (PARTITION BY product_id ORDER BY period) AS running_balance
FROM stock_movements
WHERE product_id = '...'
ORDER BY period;
```

Это быстро по конкретному товару (использует индекс `(product_id, period)`), но не для всех сразу.

**Д. Партицирование + агрегат по партиции**

Если разбить `stock_movements` по месяцам (партиции), то `SUM` по одной партиции сканирует только её — O(1 месяц), а не (вся_история).

`stock_balances` — материализованная таблица, PRIMARY KEY `(product_id, warehouse_id)`.

- Все остатки: `SELECT * FROM stock_balances` — полный скан, **O(n) по числу товаров**
- Остатки по складу: `SELECT ... WHERE warehouse_id = $1` — **O(m)** по числу товаров на складе

**Деградация есть, но линейная:**

| Товаров | Все остатки | По одному складу |
|---------|------------|------------------|
| 3 000 | ~5 ms | ~3 ms |
| 100 000 | ~30 ms | ~20 ms |
| 1 000 000 | ~200 ms | ~150 ms |

Это **один быстрый sequential scan** — для отчёта приемлемо. Если станет проблемой — добавить составной индекс `(warehouse_id, product_id)`.

---

## 4. Остатки на дату (полный скан регистра)

Вот **единственное место с реальной деградацией**. Без снапшотов:

```sql
SELECT product_id, SUM(...) - SUM(...)
FROM stock_movements
WHERE period <= '2026-03-15'
GROUP BY product_id, warehouse_id
```

| Движений | Время | Примечание |
|----------|-------|------------|
| 0 | — | нет данных |
| 3 млн | ~1–3 с | один HashAggregate, ещё терпимо |
| 30 млн | ~8–15 с | начинает быть заметно |
| 300 млн | ~60–120 с | неприемлемо для интерактивного отчёта |
| 1 млрд | ~3–5 мин | только для ночного отчёта |

**С ежедневными снапшотами** это превращается в:

| Движений | Снапшот + движения за 1 день |
|----------|------------------------------|
| любое | **10–50 ms** |

## 5. Поиск товаров (`/api/products/search`)

```sql
SELECT ... FROM products p LEFT JOIN barcodes b ...
WHERE lower(p.name) LIKE $1 OR b.barcode = $2
```

Без триграммного индекса — sequential scan по всей таблице.

| Товаров | Первый поиск | С GIN-индексом |
|---------|-------------|----------------|
| 3 000 | ~5 ms | ~2 ms |
| 100 000 | ~30 ms | ~3 ms |
| 1 000 000 | ~200 ms | ~5 ms |

**Деградация есть**, но лечится индексом:

```sql
CREATE INDEX idx_products_search ON products USING gin (to_tsvector('russian', name));
```

После него — O(log n) по индексу, ~2–5 ms для любого объёма.

## 6. Пересчёт `stock_balances` (полный)

Единственная операция, где **деградация неизбежна**:

```sql
INSERT INTO stock_balances
SELECT product_id, warehouse_id, SUM(...)
FROM stock_movements GROUP BY product_id, warehouse_id
```

| Движений | Товаров | Время |
|----------|---------|-------|
| 3 млн | 3 000 | ~300–500 ms |
| 30 млн | 30 000 | ~2–4 s |
| 300 млн | 300 000 | ~15–30 s |
| 1 млрд | 1 млн | ~60–120 s |

Но пересчёт — **редкая операция**, не на каждый клик.

## Сводная таблица деградации

| Операция | Частота | Деградация при 3 млн → 1 млрд движений |
|----------|---------|---------------------------------------|
| **Проведение документа** | каждые секунды | **нет** — всегда O(k) |
| **Отмена проведения** | редко | **нет** — всегда O(k) |
| **Текущие остатки** | каждые минуты | линейная: 5 ms → 200 ms |
| **Остатки на дату (без снапшотов)** | редко | **существенная**: 2 s → 5 min |
| **Остатки на дату (со снапшотами)** | редко | **нет**: 10–50 ms всегда |
| **Поиск товаров (без индекса)** | часто | линейная |
| **Поиск товаров (с GIN)** | часто | **нет**: 2–5 ms |
| **Полный пересчёт `stock_balances`** | очень редко | линейная: 0.5 s → 2 min |
| **Логин/Auth** | редко | **нет** — PK lookup |

---

## Вывод

Деградация проявляется **только в двух местах**:

1. **Остатки на дату** — полностью решается ежедневными снапшотами (нужно добавить)
2. **Полный пересчёт остатков** — редкая операция, для магазина на 300 товаров и 300 тыс. документов/год пересчёт будет ~100 ms через 10 лет

Всё остальное O(k) или O(log n) — не зависит от роста БД. **Основные операции (проведение, чек, остатки)** не будут деградировать даже на миллиарде документов.
