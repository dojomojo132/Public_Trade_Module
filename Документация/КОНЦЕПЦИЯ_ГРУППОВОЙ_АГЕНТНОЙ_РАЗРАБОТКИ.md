# Концепция групповой агентной параллельной разработки

> **Статус:** Draft v1.0 | **Дата:** 2026-03-19  
> **Применимость:** Любые проекты (не 1С-специфично)

---

## 1. ОБЗОР СИСТЕМЫ

### Участники

```
┌─────────────────────────────────────────────────────────────┐
│                    ORCHESTRATOR AGENT                       │
│  • Видит весь проект целиком                               │
│  • Декомпозирует задачи                                    │
│  • Маршрутизирует работу                                   │
│  • Управляет состоянием (pause/resume/stop)                │
│  • Разрешает конфликты                                     │
└────────────────────────┬────────────────────────────────────┘
                         │ Task Bus (файлы / API / git)
         ┌───────────────┼───────────────────────┐
         │               │               │       │
    ┌────▼────┐    ┌─────▼────┐    ┌────▼────┐  ┌────▼────┐
    │ Agent 1 │    │ Agent 2  │    │ Agent 3 │  │ Agent 4 │
    │Frontend │    │ Backend  │    │  Tests  │  │  Docs   │
    │ PC-1    │    │  PC-2    │    │  PC-2   │  │  PC-1   │
    └─────────┘    └──────────┘    └─────────┘  └─────────┘
```

### Ключевые принципы

| Принцип | Описание |
|---------|---------|
| **Направления независимы** | На каждое направление (frontend/backend/tests/etc) — свой агент |
| **Оркестратор — решатель** | Только оркестратор видит зависимости между задачами |
| **Агент не выбирает задачу** | Агент берёт первую доступную задачу в своей очереди |
| **Git — единственный источник истины** | Все изменения через git, не напрямую |
| **Атомарность перехода** | Задача либо выполнена, либо откат — нет "почти готово" |

## 2. УРОВНИ РЕАЛИЗАЦИИ

### Уровень 1 — Git Bus (минимум, без инфраструктуры)

Подходит для: агенты на разных PC, общий git-репозиторий

```
Репозиторий/
└── .agent-bus/
    ├── tasks/
    │   ├── pending/    ← оркестратор пишет сюда
    │   ├── active/     ← агент перемещает при старте
    │   ├── done/       ← агент перемещает при завершении
    │   └── failed/     ← при ошибке
    ├── agents/
    │   ├── agent-1/
    │   │   ├── status.json   ← heartbeat агента
    │   │   └── inbox.json    ← команды оркестратора
    │   └── ...
    └── orchestrator/
        ├── state.json        ← граф задач, статус проекта
        └── queue.json        ← очередь следующих задач
```

**Цикл работы:**
```
Оркестратор → пишет task.json → git push
    ↓
Агент → git pull каждые N сек → видит task.json → берёт задачу
    ↓
Агент → пишет status=active → git push
    ↓
Агент → выполняет работу → пишет result.json → git push
    ↓
Оркестратор → git pull → читает result → выдаёт следующую задачу
```

**Задержка:** 10–30 сек (зависит от интервала git pull)  
**Плюсы:** Нет серверов, история изменений, бесплатно  
**Минусы:** Latency, возможные конфликты при одновременном push

---

### Уровень 2 — File Bus + SQLite (рекомендуемый, одна сеть)

Подходит для: агенты в одной локальной сети, общая папка (SMB/NFS)

```
\\server\agent-bus\         ← или /mnt/agent-bus/
├── bus.db                  ← SQLite (атомарные операции)
├── tasks/                  ← файлы задач (for agent context)
└── results/                ← файлы результатов
```

**Задержка:** < 1 сек  
**Плюсы:** Атомарность SQLite, быстро, просто  
**Минусы:** Требует общей папки, нет версионирования

---

### Уровень 3 — REST API Bus (production, кросс-интернет)

Подходит для: агенты на разных ПК в разных сетях

```
Orchestrator PC:
  FastAPI сервер :8765
      + Tailscale/ngrok для доступа извне

Agent PCs:
  agent_worker.py → HTTP polling → /api/tasks/next
                 → HTTP POST   → /api/tasks/{id}/result
```

**Задержка:** < 0.5 сек (long-polling)  
**Плюсы:** Работает через интернет, масштабируемо  
**Минусы:** Нужен сервер, сеть

### Возможные статусы агента

| Статус | Значение |
|--------|---------|
| `idle` | Ожидает задачи |
| `working` | Выполняет задачу |
| `paused` | Оркестратор приостановил |
| `stopped` | Не принимает задачи |
| `error` | Критическая ошибка |
| `offline` | Нет heartbeat > 5 мин |

## 5. INBOX — КОМАНДЫ ОРКЕСТРАТОРА

Оркестратор пишет команды в `.agent-bus/agents/agent-N/inbox.json`:

```json
{
  "commands": [
    {
      "command_id": "cmd-001",
      "timestamp": "2026-03-19T10:10:00Z",
      "type": "pause",
      "reason": "Ждём завершения backend задачи (зависимость)"
    }
  ]
}
```

### Типы команд оркестратора

| Команда | Действие агента |
|---------|----------------|
| `pause` | Завершить текущий шаг, заморозить |
| `resume` | Продолжить работу |
| `stop` | Завершить после текущей задачи |
| `cancel_task` | Отменить текущую задачу |
| `priority_override` | Взять задачу вне очереди |
| `context_sync` | Обновить общий контекст |

## 6. АЛГОРИТМ ОРКЕСТРАТОРА

```python
# Псевдокод основного цикла оркестратора

def orchestrator_loop():
    while True:
        # 1. Получить статусы агентов
        agent_statuses = bus.get_all_agent_statuses()
        
        # 2. Обнаружить проблемы
        for agent in agent_statuses:
            if agent.is_offline():
                handle_offline_agent(agent)  # переназначить задачу
            if agent.is_stuck():
                send_command(agent, "cancel_task")
        
        # 3. Проверить завершённые задачи
        done_tasks = bus.get_done_tasks()
        for task in done_tasks:
            # разблокировать зависимые задачи
            unblock_dependent_tasks(task.id)
        
        # 4. Назначить готовые задачи
        ready_tasks = bus.get_ready_tasks()  # depends_on выполнены
        idle_agents = [a for a in agent_statuses if a.status == "idle"]
        
        for task in ready_tasks:
            agent = find_best_agent(task, idle_agents)
            if agent:
                bus.assign_task(task.id, agent.id)
        
        # 5. Обновить state.json
        bus.update_project_state()
        
        sleep(POLL_INTERVAL)  # 5-10 сек


def find_best_agent(task, idle_agents):
    """Выбрать агента по направлению и capabilities"""
    candidates = [a for a in idle_agents 
                  if task.direction == a.direction]
    if not candidates:
        return None
    # По незагруженности (context_window_used)
    return min(candidates, key=lambda a: a.context_window_used)
```

## 7. АЛГОРИТМ АГЕНТА

```python
# Псевдокод основного цикла агента

def agent_loop(agent_id, direction):
    while True:
        # 1. Heartbeat
        bus.update_status(agent_id, heartbeat=now())
        
        # 2. Проверить inbox
        commands = bus.read_inbox(agent_id)
        for cmd in commands:
            if cmd.type == "pause":
                wait_for_resume(agent_id)
            elif cmd.type == "stop":
                return
        
        # 3. Взять задачу
        task = bus.claim_next_task(agent_id, direction)
        if not task:
            sleep(POLL_INTERVAL)
            continue
        
        # 4. Выполнить задачу
        bus.update_status(agent_id, status="working", current_task=task.id)
        bus.move_task(task.id, "active")
        
        try:
            result = execute_task(task)  # ← ЗДЕСЬ РАБОТАЕТ АГЕНТ
            bus.complete_task(task.id, result)
            bus.move_task(task.id, "done")
        except Exception as e:
            bus.fail_task(task.id, error=str(e))
            bus.move_task(task.id, "failed")
        
        bus.update_status(agent_id, status="idle", current_task=None)
        sleep(1)
```

## 8. ГРАФ ЗАВИСИМОСТЕЙ ЗАДАЧ

Оркестратор хранит DAG (направленный ацикличный граф) зависимостей:

```
state.json:
{
  "project": "MyProject",
  "phase": "Sprint-1",
  "task_graph": {
    "task-001": { "status": "done",    "blocks": ["task-003", "task-004"] },
    "task-002": { "status": "active",  "blocks": ["task-005"] },
    "task-003": { "status": "pending", "depends_on": ["task-001"], "blocks": [] },
    "task-004": { "status": "pending", "depends_on": ["task-001"], "blocks": ["task-006"] },
    "task-005": { "status": "pending", "depends_on": ["task-002"], "blocks": [] },
    "task-006": { "status": "blocked", "depends_on": ["task-004"], "blocks": [] }
  },
  "directions": {
    "frontend": { "agent": "agent-1", "active_tasks": 1 },
    "backend":  { "agent": "agent-2", "active_tasks": 1 },
    "tests":    { "agent": "agent-3", "active_tasks": 0 },
    "docs":     { "agent": "agent-4", "active_tasks": 0 }
  }
}
```

**Визуализация:**
```
[task-001 done] ──┬──→ [task-003 → agent-1]
                  └──→ [task-004 → agent-1] ──→ [task-006 blocked]
[task-002 active] ───→ [task-005 → agent-3]
```

## 9. GIT WORKFLOW ДЛЯ АГЕНТОВ

Каждый агент работает в своей ветке:

```bash
# Агент при старте задачи:
git checkout -b feature/{direction}/{task_id}
git pull origin main

# ... выполняет работу ...

# Агент при завершении:
git add .
git commit -m "Agent-1: {task.title} [{task_id}]"
git push origin feature/{direction}/{task_id}

# Оркестратор:
# Видит push → делает MR/PR или сразу merge в зависимости от стратегии
```

**Стратегии merge:**
- `auto-merge` — оркестратор автоматически вливает при успехе тестов
- `review-required` — оркестратор создаёт MR, ждёт одобрения
- `staged` — сначала в dev, потом в main

## 10. ОБРАБОТКА КОНФЛИКТОВ И СБОЕВ

### Агент упал (offline)

```python
# Оркестратор обнаружил: heartbeat > 5 мин
if agent.last_heartbeat < now() - timedelta(minutes=5):
    # 1. Вернуть active задачу в pending
    bus.reset_task_to_pending(agent.current_task_id)
    # 2. Отметить агента offline
    bus.update_agent_status(agent.id, "offline")
    # 3. Переназначить задачу другому агенту
    bus.assign_task(task_id, find_fallback_agent(task))
```

### Задача застряла (stuck)

```python
# Оркестратор обнаружил: задача active > MAX_DURATION
if task.age_minutes > task.estimated_minutes * 2:
    send_command(agent, "cancel_task", reason="Timeout exceeded")
    # Вариант A: Разбить задачу на более мелкие
    split_task(task)
    # Вариант B: Эскалировать оркестратору как проблему
    orchestrator.escalate(task)
```

### Git конфликт при merge

```python
# Оркестратор при merge конфликте:
def handle_merge_conflict(task_a, task_b):
    # Приостановить агента B (пришёл позже)
    send_command(agent_b, "pause")
    # Дать агенту A время merge
    # После успеха — разбудить агента B с обновлённой базой
    send_command(agent_b, "context_sync", branch="main")
    send_command(agent_b, "resume")
```

## 12. ПРИМЕР РЕАЛЬНОГО СЦЕНАРИЯ

**Задача:** Добавить новую страницу "Аналитика" в webapp

**Оркестратор декомпозирует:**
```
task-001 [backend]  → Создать API endpoint /api/analytics
task-002 [frontend] → BLOCKED: ждёт task-001
task-003 [tests]    → BLOCKED: ждёт task-002
task-004 [docs]     → Написать документацию API (параллельно с task-001)
```

**Хронология:**
```
T+0:00  Оркестратор → task-001 → agent-2 (backend)
T+0:00  Оркестратор → task-004 → agent-4 (docs) — параллельно!
T+0:10  Agent-2 active: пишет endpoint
T+0:10  Agent-4 active: пишет docs
T+0:25  Agent-2 done: endpoint готов, push
T+0:25  Оркестратор: task-001 done → разблокирует task-002
T+0:25  Оркестратор → task-002 → agent-1 (frontend)
T+0:27  Agent-4 done: docs готовы, push
T+0:40  Agent-1 active: пишет страницу
T+0:55  Agent-1 done: страница готова, push
T+0:55  Оркестратор: task-002 done → разблокирует task-003
T+0:55  Оркестратор → task-003 → agent-3 (tests)
T+1:10  Agent-3 done: тесты написаны и проходят ✓
T+1:10  Оркестратор: все задачи сделаны → merge в main
```

**Итого: 70 мин вместо ~180 мин (последовательно)** — экономия 60%
