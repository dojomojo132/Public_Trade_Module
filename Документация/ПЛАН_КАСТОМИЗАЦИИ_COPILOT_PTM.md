# План кастомизации Copilot для PTM

> **Дата:** 2026-03-10
> **Цель:** превратить результаты исследования в рабочий план для агента GitHub Copilot в проекте PTM
> **Фокус:** готовые skills, custom agents, prompts, hooks и MCP-серверы, которые можно сразу адаптировать под 1С:Предприятие 8.3.27

---

## Исходное состояние

### Уже есть в проекте

- Подключен основной MCP-сервер `mcp_mcp_1c_torgov` с инструментами по метаданным, данным, отчётам, формам, объектам и администрированию.
- Подключен отладочный MCP-сервер `mcp_ptm-debug` для breakpoints, step-by-step отладки и вычисления выражений.
- Есть основной файл инструкций `.github/copilot-instructions.md`, в котором уже зафиксированы правила по BSL, XML, деплою, валидации и безопасности.
- Есть развитая документация проекта, включая спецификации, технические стандарты, шаблоны и регламенты деплоя.

### Чего пока нет

- Нет папки `.github/agents/`.
- Нет папки `.github/skills/`.
- Нет папки `.github/prompts/`.
- Нет папки `.github/hooks/`.
- Нет специализированных `.instructions.md` по маскам файлов `**/*.bsl` и `**/*.xml`.

### Вывод

Проект уже хорошо подготовлен по доменной логике и MCP-инструментам, но слой кастомизации Copilot почти полностью отсутствует. Значит, основная задача не в поиске новых MCP-серверов, а в упаковке уже существующих правил проекта в удобную агентную архитектуру.

## Оценка готовых MCP-серверов для PTM

### MCP-серверы, которые уже покрывают основную ценность

#### `mcp_mcp_1c_torgov`

Покрывает:
- анализ метаданных;
- получение структуры объектов;
- работу с формами и модулями;
- выполнение запросов 1С;
- работу с документами, справочниками и регистрами;
- smoke-тесты форм;
- экспорт данных;
- мониторинг ошибок и технического журнала.

#### `mcp_ptm-debug`

Покрывает:
- запуск debug-сессии;
- attach к отладчику;
- установку breakpoint;
- step over / step into / continue;
- стек вызовов;
- вычисление выражений в контексте остановки.

### MCP-серверы, которых не нашли в пригодном виде

- Готовый MCP для валидации XML конфигурации 1С.
- ~~Готовый MCP для синхронизации двух каталогов~~ (упразднено 2026-03-14 — единая папка `Конфигурация/`).
- Готовый MCP для безопасного orchestration деплоя PTM по нашему регламенту.
- Готовый MCP для BSL-специфичных стандартов 1С уровня PTM.

### Решение по MCP

На первом этапе **не расширять** стек внешними MCP-серверами. Для PTM уже достаточно текущих `mcp_mcp_1c_torgov` и `mcp_ptm-debug`.

Новые MCP-серверы стоит делать только позже, если появится явная боль в одном из сценариев:

1. XML-валидация до деплоя.
2. Автоматическая синхронизация двух каталогов конфигурации.
3. Управление пайплайном `Dump -> Validate -> Load -> Update -> Designer -> Monitor` как единым инструментом.

## Какие артефакты нужно сделать в первую очередь

## Этап 1. Быстрые улучшения с высокой отдачей

### 1. `bsl.instructions.md`

Назначение:
- автоматически применять правила для BSL-файлов;
- напоминать про директивы `&НаКлиенте`, `&НаСервере`, `#Область`;
- запрещать конструкции из негативного словаря;
- требовать `get_errors` после любого изменения BSL.

Почему это важно:
- даёт эффект сразу во всех `.bsl` файлах;
- снижает число синтаксических и методологических ошибок без запуска отдельного агента.

### 2. `xml-1c.instructions.md`

Назначение:
- автоматически применять правила к XML конфигурации 1С;
- напоминать про шаблоны, `version="2.20"`, полный набор `xmlns`;
- контролировать `Configuration.xml`, `ConfigDumpInfo.xml`, формы и child objects;
- контролировать единую рабочую папку `Конфигурация/` (деплой напрямую).

Почему это важно:
- XML-ошибки в PTM дороже и опаснее BSL-ошибок;
- это лучший способ встроить предохранители до деплоя.

## Этап 2. Доменные skills

### 3. Skill `1c-deploy`

Должен описывать:
- обязательный локальный бэкап;
- чтение `КРИТИЧЕСКИЕ_ОШИБКИ.md`;
- `deploy-config.ps1 -Action Dump` перед правками;
- валидацию и деплой;
- открытие конфигуратора;
- мониторинг ошибок после деплоя.

### 4. Skill `1c-form-generator`

Должен описывать:
- использование генератора форм;
- корректную структуру `Forms/`;
- обязательные три файла формы;
- правила id элементов;
- обновление `ConfigDumpInfo.xml` и родительского объекта.

### 5. Skill `1c-bsl-review`

Должен описывать:
- типовые антипаттерны PTM;
- проверки асинхронности;
- проверки сервер/клиент контекста;
- типовые ошибки BSL в проекте.

### 6. Skill `1c-metadata-check`

Должен описывать:
- какие MCP-вызовы обязательны до изменения объекта;
- как проверять существование объекта, формы, реквизита, табличной части;
- как отличать актуальную структуру ИБ от устаревшего файла на диске.

---

## Этап 3. Специализированные агенты

### 7. `orchestrator.agent.md`

Роль:
- координатор сложных задач;
- выбирает, кого вызвать: разработчика, ревьюера, исследователя, деплой-исполнителя;
- подходит для больших multi-step задач.

Поведение:
- сначала уточняет тип задачи;
- затем делегирует подзадачи в узкоспециализированные агенты;
- собирает итоговое решение в одном ответе.

### 8. `1c-developer.agent.md`

Роль:
- основной агент разработки PTM;
- работает по правилам 1С, MCP и локального деплоя;
- не придумывает структуру метаданных, а проверяет её через MCP.

Должен уметь:
- безопасно изменять BSL и XML;
- соблюдать workflow PTM;
- использовать skill-и `1c-deploy`, `1c-form-generator`, `1c-metadata-check`.

---

## Этап 4. Повторяемые prompts

### 9. `ptm-new-task.prompt.md`

Сценарий:
- старт новой задачи по регламенту PTM;
- бэкап, dump, анализ объекта, реализация, валидация, деплой, мониторинг.

### 10. `ptm-fix-deploy.prompt.md`

Сценарий:
- разбор ошибок деплоя;
- чтение полного лога;
- исправление XML/BSL;
- повторный деплой;
- эскалация к rollback после нескольких неудач.

### 11. `ptm-review.prompt.md`

Сценарий:
- обзор изменений в режиме code review;
- приоритет: баги, риски, регрессии, нарушение регламента PTM.

---

## Этап 5. Hooks и дополнительные предохранители

### 12. `guardrails.json`

Использовать осторожно. Hooks должны быть только мягкими и недеструктивными.

Цель hooks:
- напоминать о необходимости dump перед правками;
- напоминать о проверке `КРИТИЧЕСКИЕ_ОШИБКИ.md`;
- напоминать о `get_errors` после генерации BSL/XML.

Чего не делать hooks:
- не запускать автоматически долгие и рискованные операции;
- не делать автоматический деплой без явного намерения агента;
- не модифицировать файлы за пользователя скрыто.

## Что именно брать из найденных готовых решений

### Брать почти без изменений

- Общую структуру `.github/agents`, `.github/skills`, `.github/prompts`, `.github/hooks` из документации VS Code.
- Паттерн coordinator/worker и planner/explorer/analyst из `jaktestowac/awesome-copilot-for-testers`.
- Подход к узкой специализации агентов из `trsdn/github-copilot-agent`.

### Брать как ориентир, но адаптировать сильно

- Community prompt libraries.
- Community examples hooks.
- Общие reusable skill templates.

### Не брать как готовое решение

- Любые generic DevOps/MCP recipes без учёта 1С и PTM.
- Общие XML validators без знания структуры 1С.
- Skills, рассчитанные на JS/TS/Python-проекты без двухкаталожной структуры конфигурации.

## Риски и ограничения

1. Главная сложность PTM не в кодогенерации, а в соблюдении процесса: backup, dump, MCP-проверка, валидация, деплой, мониторинг.
2. Один общий `copilot-instructions.md` уже перегружен. При дальнейшем росте его нужно оставить umbrella-файлом, а детальные правила вынести в skills и file-based instructions.
3. Нельзя переносить generic community-решения в проект без адаптации под 1С XML, BSL и dual-folder workflow.
4. Hooks могут принести больше вреда, чем пользы, если начнут автоматически запускать рискованные команды.
5. Новые MCP-серверы нужно делать только после того, как станет ясно, что текущих двух серверов действительно недостаточно.

## Рабочее решение для агента

Если агенту нужно выбрать, с чего начинать реализацию, порядок должен быть таким:

1. Создать `bsl.instructions.md`.
2. Создать `xml-1c.instructions.md`.
3. Создать skill `1c-deploy`.
4. Создать skill `1c-form-generator`.
5. После этого переходить к custom agents.

Это даст максимальную пользу при минимальном риске и не потребует немедленного изменения MCP-слоя.

## Definition of Done для первой волны

Первая волна кастомизации считается завершённой, когда в проекте появятся:

1. `.github/instructions/bsl.instructions.md`
2. `.github/instructions/xml-1c.instructions.md`
3. `.github/skills/1c-deploy/SKILL.md`
4. `.github/skills/1c-form-generator/SKILL.md`

И когда эти артефакты будут явно закреплять:

- обязательный `Dump` перед изменениями;
- обязательную MCP-проверку структуры объекта;
- обязательный `get_errors` после генерации BSL/XML;
- обязательную работу с двумя каталогами конфигурации;
- обязательную валидацию, деплой и мониторинг.
