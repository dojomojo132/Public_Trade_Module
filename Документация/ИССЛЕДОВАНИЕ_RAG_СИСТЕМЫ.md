# Исследование RAG-системы и её применение в проекте PTM

> Дата: 10 марта 2026
> Источники: AWS, IBM Research, Pinecone, Microsoft Research (GraphRAG), LlamaIndex, Anthropic (Contextual Retrieval)

---

## 1. Что такое RAG (Retrieval-Augmented Generation)

**RAG** — техника, которая расширяет возможности LLM за счёт подключения внешней базы знаний. Вместо того чтобы полагаться только на данные, на которых модель обучалась, RAG **извлекает релевантную информацию** из внешнего хранилища и подаёт её в контекст запроса.

### Ключевая аналогия
> «Разница между экзаменом с открытой книгой и закрытой книгой» — IBM Research

### 4 ключевых компонента RAG

| Этап | Что происходит |
|------|---------------|
| **1. Ingestion (загрузка)** | Документы разбиваются на чанки, преобразуются в векторные эмбеддинги, загружаются в векторную БД |
| **2. Retrieval (извлечение)** | По запросу пользователя ищутся наиболее релевантные чанки (семантический + лексический поиск) |
| **3. Augmentation (дополнение)** | Найденные чанки объединяются с запросом пользователя в расширенный промпт |
| **4. Generation (генерация)** | LLM генерирует ответ, используя контекст из найденных данных |

### Зачем RAG нужен

- **Актуальность**: LLM имеют дату «отсечки» обучающих данных — RAG даёт доступ к свежей информации
- **Точность**: Снижает галлюцинации, заземляя ответы на реальных данных
- **Доверие**: Можно указать источники, ссылки на документы
- **Экономичность**: Дешевле, чем файн-тюнинг или переобучение модели
- **Контроль**: Разработчик управляет источниками данных и уровнями доступа

## 2. Продвинутые техники RAG (2025-2026)

### 2.1 Hybrid Search (гибридный поиск)
Комбинация **семантического поиска** (dense vectors / embeddings) и **лексического поиска** (sparse vectors / BM25):

- Семантический поиск находит документы по смыслу
- BM25 находит точные совпадения ключевых слов, терминов, кодов
- Результаты объединяются через **rank fusion**

> Особенно важно для доменов с уникальной терминологией (1С: «ТабличнаяЧасть», «РегистрНакопления», «Справочник.Контрагенты»)

### 2.2 Contextual Retrieval (Anthropic)
Революционная техника от Anthropic (сентябрь 2024):

1. Перед эмбеддингом каждый чанк **обогащается контекстом** всего документа
2. LLM генерирует краткое описание (50-100 токенов), объясняющее чанк в контексте документа
3. Это описание **препендится** к чанку перед эмбеддингом

**Результаты**:
- Contextual Embeddings: снижение ошибок поиска на **35%**
- Contextual Embeddings + BM25: **-49%**
- + Reranking: **-67%**

### 2.3 Reranking (переранжирование)
После начального поиска (top-150) применяется модель ре-ранкинга:

1. Получить топ-150 потенциально релевантных чанков
2. Прогнать через модель ре-ранкинга (Cohere, Voyage)
3. Оставить топ-20 по релевантности
4. Подать в LLM

### 2.4 GraphRAG (Microsoft Research)
Использует **граф знаний**, созданный LLM, вместо простого векторного поиска:

- LLM обрабатывает весь датасет, создаёт граф сущностей и связей
- Граф кластеризуется иерархически
- При запросе используются и граф, и кластеры для ответа

**Преимущества GraphRAG**:
- Отвечает на вопросы, требующие «соединения точек» из разных документов
- Поддерживает вопросы уровня всего датасета («Какие 5 главных тем?»)
- Обеспечивает provenance — ссылки на исходные данные

### 2.5 Agentic RAG
Агенты-оркестраторы управляют компонентами RAG:

- Формируют более эффективные запросы
- Выбирают инструменты поиска
- Оценивают качество найденного контекста
- Применяют reasoning для валидации
- Итеративно уточняют запросы

## 4. Применение RAG в проекте PTM

### 4.1 Текущая архитектура проекта (что у нас уже есть)

Проект PTM уже использует **элементы RAG-подхода** без векторной БД:

| Компонент | Аналог RAG | Текущая реализация |
|-----------|-----------|-------------------|
| База знаний | Documents | `.github/instructions/`, `.github/skills/`, `Документация/` |
| Контекст-инъекция | Augmentation | `copilot-instructions.md`, `*.instructions.md`, SKILL.md |
| Query routing | Router | Агенты (`orchestrator`, `1c-coder`, `1c-deployer` и др.) |
| Внешние данные | External data | MCP-сервер 1С (метаданные ИБ в реальном времени) |
| Оркестрация | Agent | Copilot Agent Mode с кастомными агентами |

**Фактически система Copilot-кастомизации PTM — это ручной RAG**, где:
- instructions = предподготовленные чанки знаний
- skills = доменные навыки, загружаемые по запросу
- agents = маршрутизаторы запросов
- MCP = live-данные из ИБ

### 4.2 Куда можно применить «настоящий» RAG

#### Сценарий A: RAG для стандартов и документации 1С

**Проблема**: Copilot не знает стандарты 1С 8.3.27, xml-структуру конфигурации, специфику PTM.

**Текущее решение**: Файлы instructions/skills (ограничение ~8000 токенов на файл).

**RAG-решение**:
```
Источники данных:
├── Документация/Технические_стандарты/*.md     (~50+ страниц)
├── Документация/Спецификации/*.xml             (ТЗ конфигурации)
├── Документация/Шаблоны/*.xml                  (XML-шаблоны)
├── syntax_1c.txt (MCP resource)                (синтаксис языка)
├── Стандарты разработки 1С (ITS)               (внешний источник)
└── Конфигурация/**/*.bsl                       (существующий код)

Векторная БД: ChromaDB (локальная, бесплатная)
Embedding: BGE-large или E5-large (open-source, локально)
Поиск: Hybrid (semantic + BM25 для терминов 1С)
```

**Выигрыш**: Вместо ручного поддержания instructions-файлов — автоматический поиск релевантной документации по контексту запроса.

#### Сценарий B: RAG для существующего кода PTM

**Проблема**: При написании нового кода Copilot не «видит» весь существующий код конфигурации.

**RAG-решение**:
```
Источники:
├── Конфигурация/**/*.bsl    (все модули)
├── Конфигурация/**/*.xml    (структура метаданных)
└── MCP: метаданные ИБ       (live-структура)

Чанкинг: по функциям/процедурам BSL
Контекст: имя модуля + тип объекта + подсистема
```

**Выигрыш**: При создании нового обработчика — автоматический поиск паттернов в существующем коде.

#### Сценарий C: RAG для диагностики ошибок

**Проблема**: При ошибках деплоя/выполнения нужно искать аналогичные случаи.

**RAG-решение**:
```
Источники:
├── Документация/КРИТИЧЕСКИЕ_ОШИБКИ.md
├── Логи деплоя (deploy logs)
├── Тесты/ (результаты тестов)
└── История git (commit messages + diffs)

Индексация: ошибки → причины → решения
```

**Выигрыш**: Автоматическая диагностика: «Эта ошибка похожа на X, решение было Y».

#### Сценарий D: GraphRAG для модели данных PTM

**Проблема**: Связи между объектами (документы → движения → регистры) сложно удержать в контексте.

**GraphRAG-решение**:
```
Граф знаний:
  Документ.ПриходТовара → [движение] → Регистр.ОстаткиТоваров
  Справочник.Номенклатура → [реквизит] → Справочник.ЕдиницыИзмерения
  Подсистема.Закупки → [содержит] → Документ.ПриходТовара
```

**Выигрыш**: Агент может ответить: «Какие объекты связаны с Номенклатурой?» или «Покажи всю цепочку движений документа ПриходТовара».

> **Примечание**: Частично это уже реализовано через MCP-ресурсы `ptm://datamodel`, `ptm://registers`, `ptm://business-logic`, но GraphRAG позволит автоматически обнаруживать неявные связи.

## 5. Рекомендуемый план внедрения RAG

### Фаза 1: Quick Win — RAG для документации (1-2 недели)

```
Стек:
  - ChromaDB (локальная векторная БД, pip install chromadb)
  - sentence-transformers (локальные эмбеддинги, бесплатно)
  - BM25 через rank-bm25 (pip install rank-bm25)

Шаги:
  1. Проиндексировать Документация/**/*.md + Конфигурация/**/*.bsl
  2. Создать Python-сервис search_docs.py
  3. Подключить как MCP-инструмент (search_documentation)
  4. Copilot Agent получает возможность искать по всей документации
```

**Инструмент MCP**:
```json
{
  "name": "search_documentation",
  "description": "Поиск по документации PTM, стандартам 1С и существующему коду",
  "parameters": {
    "query": "string — запрос на естественном языке"
  }
}
```

### Фаза 2: Code RAG — поиск по коду (2-3 недели)

```
Стек (дополнительно):
  - tree-sitter (парсинг BSL → чанки по функциям)
  - Contextual Retrieval (контекст модуля/объекта для каждого чанка)

Шаги:
  1. Парсинг BSL-модулей на функции/процедуры
  2. Каждый чанк = функция + метаданные (модуль, объект, подсистема)
  3. Contextual Retrieval: «Эта функция из модуля объекта документа ПриходТовара...»
  4. MCP-инструмент: search_code
```

### Фаза 3: Error Knowledge Base (2-3 недели)

```
Стек (дополнительно):
  - Structured error indexing
  - Автоматический сбор из логов деплоя

Шаги:
  1. Парсинг КРИТИЧЕСКИЕ_ОШИБКИ.md в структурированный формат
  2. Индексация логов деплоя (ошибка → контекст → решение)
  3. MCP-инструмент: diagnose_error
```

### Фаза 4: GraphRAG для модели данных (4-6 недель)

```
Стек:
  - Microsoft GraphRAG (pip install graphrag)
  - Neo4j или NetworkX (граф)

Шаги:
  1. Построить граф из metadata (MCP: get_connected_objects)
  2. Обогатить связями из кода (движения документов)
  3. Индексировать кластеры
  4. MCP-инструмент: explore_data_model
```

## 7. Ключевые best practices (по материалам исследования)

### Чанкинг
- Размер чанка: 200-800 токенов (оптимально ~500)
- Для BSL: чанк = одна функция/процедура
- Для XML: чанк = один объект метаданных
- Перекрытие (overlap): 50-100 токенов между соседними чанками текста

### Поиск
- **Всегда** использовать гибридный поиск (embedding + BM25)
- Для 1С-терминологии BM25 критически важен (точные имена объектов)
- Top-20 чанков лучше, чем top-5 или top-10

### Контекст
- Применять Contextual Retrieval — обогащать чанки контекстом документа
- Для BSL: «Эта процедура из модуля объекта Документ.ПриходТовара, подсистема Закупки»
- Для XML: «Этот шаблон описывает структуру справочника платформы 8.3.27»

### Evaluation (оценка качества)
- Создать набор вопросов-ответов (ground truth)
- Метрики: recall@K, precision@K, MRR
- Тестировать каждое изменение пайплайна

### Стоимость
- Локальные эмбеддинги (sentence-transformers) = **бесплатно**
- ChromaDB = **бесплатно**
- Один раз индексация ~500 BSL-файлов < 5 минут
- Incremental update при изменении файлов

## 8. Что НЕ стоит делать

| Антипаттерн | Почему |
|------------|--------|
| Засовывать всё в контекст LLM без RAG | «Lost in the middle» — модель теряет информацию в середине длинного контекста |
| Использовать только семантический поиск | Пропуск точных совпадений (имена объектов 1С, коды ошибок) |
| Файн-тюнинг вместо RAG | Дорого, сложно обновлять, не даёт ссылок на источники |
| Индексировать без чанкинга | Огромные документы = размытый эмбеддинг |
| Игнорировать evaluation | Невозможно понять, улучшается ли система |

## 9. Сравнение с текущим подходом (instructions/skills)

| Критерий | Текущий подход (instructions) | RAG-подход |
|----------|------------------------------|------------|
| Масштаб знаний | ~10 файлов, ручное поддержание | Вся документация + весь код |
| Актуальность | Ручное обновление | Автоматическая переиндексация |
| Точность поиска | Copilot решает, что загрузить | Семантический + лексический поиск |
| Стоимость поддержки | Высокая (ручная работа) | Низкая (автоматизация) |
| Скорость отклика | Мгновенно (в контексте) | +1-2 сек на поиск |
| Контроль | Полный (мы пишем инструкции) | Зависит от качества индексации |

**Рекомендация**: Комбинировать оба подхода. Instructions/skills — для критических правил, которые должны быть ВСЕГДА в контексте. RAG — для поиска релевантной информации по запросу.

## 10. Итоговые рекомендации

1. **Начать с Фазы 1** (документация → ChromaDB) — быстрый результат за 1-2 недели
2. **Использовать MCP** как точку интеграции — RAG-сервер подключается как ещё один MCP
3. **Сохранить instructions/skills** — они дополняют RAG, а не заменяются им
4. **Гибридный поиск обязателен** для 1С-терминологии
5. **Contextual Retrieval** — применить для BSL-чанков (контекст модуля/объекта)
6. **GraphRAG** рассмотреть для фазы 4 — идеально для модели данных PTM
7. **Evaluation** — создать тестовый набор вопросов по PTM для оценки качества

### Минимальный стек для старта

```bash
pip install chromadb sentence-transformers rank-bm25
```

Всё работает **локально**, **бесплатно**, без облачных сервисов.
