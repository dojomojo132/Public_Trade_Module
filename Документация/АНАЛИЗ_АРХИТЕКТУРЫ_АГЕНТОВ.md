## 2. Слои системы и правило загрузки

| Слой | Файлы | Загрузка | Назначение |
|------|-------|----------|------------|
| `copilot-instructions.md` | 1 файл, ~192 строки | **Всегда** | Роль, правила, диалоги — горячий контекст |
| `instructions/` | 2 файла | Авто по маске (`*.bsl`, `*.xml`) | Правила синтаксиса — загружаются только при работе с нужным типом файлов |
| `skills/` | 6 папок | On-demand по описанию | Детальные процедуры (деплой, отладка, ревью...) |
| `agents/` | 5 файлов | При явном вызове агента | Ролевые профили специалистов |
| `prompts/` | 8 файлов | При явном вызове пользователем | Шаблоны задач |
| `hooks/` | 7 скриптов | Автоматически | Guardrails: проверки до/после операций |

**Ключевой принцип:** `copilot-instructions.md` содержит только **уникальный** контент
(~192 строки). Всё специфичное вынесено в skills/instructions, которые загружаются по требованию.
Это снижает расход токенов контекста на ~90%.

## 3. Агенты: роли и ответственности

### 3.1 Orchestrator (`orchestrator.agent.md`)

**Роль:** Координатор сложных многошаговых задач PTM.

**Не делает сам:** BSL/XML-код. **Делает:** декомпозиция, делегирование, контроль качества.

**Полный рабочий цикл (фазы):**

```
Фаза 0: Защита данных
  ├── python scripts/_local_backup.py "описание"
  ├── Прочитать КРИТИЧЕСКИЕ_ОШИБКИ.md
  └── python scripts/_ps_wrapper.py deploy -Action Dump

Фаза 1: Анализ и планирование
  ├── 1.1 Классификация запроса → выбор маршрута делегирования
  ├── 1.2 Декомпозиция → manage_todo_list для 3+ шагов
  └── 1.3 Разведка: Obsidian KG → MCP ИБ → файлы на диске

Фаза 2: Делегирование агентам
  ├── 1c-architect → ТЗ
  ├── 1c-coder → XML/BSL реализация
  ├── 1c-form-builder → формы
  ├── 1c-deployer → деплой/мониторинг
  └── Explore → поиск файлов

Фаза 3: Контроль качества
  ├── get_errors = 0 на всех изменённых файлах
  ├── Multi-file checklist (Configuration.xml, ConfigDumpInfo.xml, подсистемы)
  └── Специфические проверки по типу объекта

Фаза 4: Деплой (через 1c-deployer)
  └── validate → Full → мониторинг (2 попытки, затем откат)

Фаза 5: Мониторинг
  └── python scripts/_ps_wrapper.py monitor -Action Check

Фаза 5.5: Интерактивная отладка (только если нужно)
  └── skill 1c-debug → debug_connect → breakpoints → фикс → debug_disconnect

Фаза R: Сверка конфигурации (ручные изменения в ИБ)
  └── Dump → MCP-анализ → Obsidian → validate

Фаза 6: Завершение
  └── Спецификация, Obsidian KG, history, ДИАЛОГ 2

Фаза 7: Замер производительности
  └── ЖУРНАЛ_ПРОИЗВОДИТЕЛЬНОСТИ.md
```

**Правило ТЗ:** Проект от `1c-architect` **ВСЕГДА** предъявляется пользователю перед передачей исполнителям.

**Правило 2 попыток:** Если деплой не исправить за 2 итерации → ОТКАТ + запись в КРИТИЧЕСКИЕ_ОШИБКИ.md.

---

### 3.2 1c-coder (`1c-coder.agent.md`)

**Роль:** BSL-разработчик + создатель XML-метаданных.

**Инструменты:** read, search, edit, execute, todo

**Обязательно ДО кода:**
1. `list_metadata_objects` — объект существует?
2. `get_metadata_structure` — реквизиты, ТЧ, типы
3. `get_form_structure` — точное имя формы
4. `Документация/КРИТИЧЕСКИЕ_ОШИБКИ.md` — предохранители

**Обязательно ПОСЛЕ кода:**
1. `get_errors` на каждый `.bsl` и `.xml`
2. Multi-file checklist: `Configuration.xml` + `ConfigDumpInfo.xml` + подсистемы
3. Obsidian KG — обновить заметки затронутых объектов

**Ключевые ограничения:**
- Не угадывать имена → только MCP
- Не деплоить → это зона 1c-deployer
- Не коммитить без подтверждения пользователя
- PowerShell + кириллица → через Python-wrapper

---

### 3.3 1c-architect (`1c-architect.agent.md`)

**Роль:** Проектировщик метаданных — создаёт ТЗ, анализирует зависимости.

**Инструменты:** read, search (только чтение!)

**Обязательно ДО проектирования:**
1. `get_configuration_overview` — обзор конфигурации
2. `list_metadata_objects` — что уже есть
3. `get_metadata_structure` + `get_connected_objects` — связи
4. `ТЕХНИЧЕСКАЯ СПЕЦИФИКАЦИЯ...xml` — бизнес-логика

**Формат выхода — ТЗ:**
- Тип объекта, имя, назначение
- Таблица реквизитов (Имя | Тип | Обязательный | Описание)
- Табличные части
- Движения по регистрам (для документов)
- Таблица форм
- Зависимости (использует, используется)
- Подсистема, риски

**Ключевое ограничение:** Реализация не начинается без явного одобрения ТЗ пользователем.

---

### 3.4 1c-deployer (`1c-deployer.agent.md`)

**Роль:** Деплой-специалист + диагностик runtime-ошибок.

**Инструменты:** read, search, edit, execute, agent

**Хуки:** PreToolUse → `deployer_pre_check.py`, PostToolUse → `deployer_post_check.py`

**Маршрутизация ошибок деплоя:**

| Признак ошибки | Куда |
|---|---|
| `Form.xml`, `id`, `ContextMenu` | → 1c-form-builder |
| `Catalogs/`, `Documents/`, `ChildObjects` | → 1c-coder |
| `{Модуль(строка, колонка)}: текст` | → 1c-coder |
| `EXIT_CODE: -2` (таймаут) | → ОТКАТ немедленно |
| `EXIT_CODE: 10` (бэкап) | → проверить доступ к ИБ |

---

### 3.5 1c-form-builder (`1c-form-builder.agent.md`)

**Роль:** Специалист по формам — Form.xml, дескрипторы, модули форм.

**Инструменты:** read, search, edit, execute, todo

**Хуки:** PostToolUse → `form_builder_post_create.py`

**Главный инструмент:** `python scripts/_generate_form.py`

**Правило ID элементов:**
```
AutoCommandBar формы       → id="-1" ВСЕГДА
Остальные элементы         → последовательная нумерация от 1
ContextMenu родителя N     → id=N+1
ExtendedTooltip родителя N → id=N+2
```

## 4. Навыки (Skills): детальный разбор

### 4.1 skill: 1c-deploy

**Назначение:** Полный цикл деплоя — бэкап, валидация, загрузка, мониторинг, откат, git commit.

**Команды (все через Python-wrapper):**
```bash
python scripts/_ps_wrapper.py deploy -Action Full       # полный цикл
python scripts/_ps_wrapper.py deploy -Action Dump       # ИБ → файлы
python scripts/_ps_wrapper.py deploy -Action Backup     # бэкап ИБ
python scripts/_ps_wrapper.py deploy -Action Rollback   # откат
python scripts/_ps_wrapper.py validate                  # валидация XML
python scripts/_ps_wrapper.py monitor -Action Check -LastMinutes 5
```

**Оптимизации:**
- `-SkipDtBackup` — пропустить DT-бэкап (MCP блокирует ИБ)
- `-SkipCheck` — пропустить CheckConfig (~40 сек, если BSL уже проверен)

**Правило 7 этапов деплоя:**
1. Защита данных (бэкап + чтение КРИТИЧЕСКИЕ_ОШИБКИ.md)
2. Валидация (`validate`)
3. Деплой (`Full`)
4. Разбор ошибок (блок `=== ОШИБКИ (для Copilot Agent) ===`)
5. Откат (при 2 неудачах)
6. Мониторинг (ТЖ + ЖР)
7. Git commit (только после подтверждения пользователя)

### 4.3 skill: 1c-bsl-review

**Назначение:** Проверка BSL-кода на антипаттерны и нарушения стандартов PTM.

**Чеклист ревью (8 категорий):**
1. Автоматическая проверка (`get_errors`)
2. Негативный словарь (устаревшие методы, неверные конструкторы)
3. Структура модуля (директивы, `#Область`)
4. Асинхронность (только `Асинх`/`Ждать` на клиенте)
5. Запросы (псевдонимы, `ЕСТЬNULL`, нет запросов в циклах)
6. Транзакции (паттерн `НачатьТранзакцию → Попытка → Зафиксировать/Отменить`)
7. Безопасность (`Выполнить()` с переменной, хардкод паролей)
8. Проведение документов (первая строка `ОбменДанными.Загрузка`)

### 4.4 skill: 1c-debug ← **ПРИЧИНА НЕИСПОЛЬЗОВАНИЯ**

**Назначение:** HTTP-отладка 1С через RDBG-протокол.

**Архитектура (реализована в `scripts/debug/`):**
```
VS Code Agent (MCP tools/call)
    ↓ JSON-RPC stdio
scripts/debug/debug_mcp_server.py  ← MCP-сервер
    ↓ Python API
scripts/debug/session.py           ← менеджер сессии + polling thread
    ├── rdbg_client.py → HTTP/XML → dbgs.exe (RDBG-сервер)
    ├── launcher.py    → управление dbgs.exe + 1cv8c.exe
    └── metadata_mapper.py → BSL-путь → UUID модуля
```

**Конфигурация (`scripts/debug/debug_config.json`):**
```json
{
  "platform": { "root": "C:\\Program Files\\1cv8\\8.3.27.1741" },
  "infoBase": { "path": "D:\\Bases\\PTM", "user": "Admin" },
  "debug": { "host": "localhost", "portRange": [1550, 1560] },
  "workspace": { "configRoot": "D:\\Git\\Public_Trade_Module\\Конфигурация" }
}
```

**13 инструментов MCP-сервера ptm-debug:**

| Инструмент | Описание |
|-----------|----------|
| `debug_connect` | Запуск dbgs.exe + attach + polling (ВЫЗЫВАТЬ ПЕРВЫМ) |
| `debug_disconnect` | Завершение сессии (detach + kill процессов) |
| `debug_launch` | Запуск 1С:Предприятие в режиме отладки |
| `debug_set_breakpoints` | Установить breakpoints (`file_path`, `lines[]`) |
| `debug_clear_breakpoints` | Очистить breakpoints |
| `debug_continue` | Продолжить выполнение (F5) |
| `debug_step_over` | Шаг через (F10) |
| `debug_step_into` | Шаг в (F11) |
| `debug_step_out` | Шаг из (Shift+F11) |
| `debug_get_stack` | Стек вызовов с путями к BSL |
| `debug_get_variables` | Локальные переменные текущего фрейма |
| `debug_evaluate` | Вычислить BSL-выражение |
| `debug_status` | Полный статус сессии |

**⚠️ Почему ptm-debug не использовался:**

До текущего момента скрипты MCP-сервера (`scripts/debug/`) отсутствовали в репозитории.
Skill-спецификация (`.github/skills/1c-debug/SKILL.md`) была написана как ТЗ,
но реализация не была выполнена. Агент не мог вызвать `debug_connect`, так как
MCP-сервер `ptm-debug` не запускался — нечего было запускать.

**Статус после исправления:**
- ✅ `scripts/debug/debug_config.json` — конфигурация
- ✅ `scripts/debug/rdbg_client.py` — HTTP/XML RDBG-клиент
- ✅ `scripts/debug/metadata_mapper.py` — маппинг BSL → UUID
- ✅ `scripts/debug/launcher.py` — управление процессами
- ✅ `scripts/debug/session.py` — менеджер сессии + polling
- ✅ `scripts/debug/debug_mcp_server.py` — MCP-сервер ptm-debug

**Команда запуска MCP-сервера:**
```bash
python scripts/debug/debug_mcp_server.py --config scripts/debug/debug_config.json
```

**Требование для активации:** Заполнить `debug_config.json` актуальными путями
(`platform.root`, `infoBase.path`) и зарегистрировать MCP-сервер в VS Code (`.vscode/mcp.json`).

## 5. Инструкции (Instructions): детальный разбор

### 5.1 bsl.instructions.md

**Триггер:** `**/*.bsl` — загружается автоматически при работе с BSL-файлами

**Ключевые разделы:**
- Директивы компиляции (обязательны перед каждым методом)
- Области (`#Область ... #КонецОбласти`) — весь код внутри
- Именование (русский ВерблюжийРегистр, глагол+существительное)
- Конструктор: ТОЛЬКО `Новый` (не `Новая`, не `Новое`)
- Асинхронность (`Асинх`/`Ждать`, запрет модальных вызовов)
- Запросы (псевдонимы, `ЕСТЬNULL`, нет в циклах, параметры через `УстановитьПараметр`)
- Транзакции (паттерн с блокировкой данных)
- Безопасность (запрет `Выполнить()` с переменной)

### 5.2 xml-1c.instructions.md

**Триггер:** `**/*.xml` — загружается автоматически при работе с XML-файлами

**Ключевые разделы:**
- Эталонный заголовок `MetaDataObject` (17 xmlns + `version="2.20"`)
- Multi-file checklist (5 файлов при создании объекта)
- ConfigDumpInfo.xml (формат + `configVersion`)
- Маппинг типов → папок
- Типичные ошибки (неполные xmlns, version="2.0", дублирующиеся id)

## 6. Хуки (Hooks): автоматические guardrails

### 6.1 guardrails.json

Конфигурация хуков:
- **SessionStart** → `session_start.py` (инициализация сессии)
- **PreToolUse** → `pre_edit_check.py` + агентоспецифичные
- **PostToolUse** → агентоспецифичные скрипты

### 6.2 Скрипты хуков

| Скрипт | Когда | Назначение |
|--------|-------|------------|
| `session_start.py` | При старте сессии | Инициализация контекста |
| `pre_edit_check.py` | Перед любым редактированием | Общие проверки |
| `deployer_pre_check.py` | Перед операциями деплоя | Проверка готовности к деплою |
| `deployer_post_check.py` | После операций деплоя | Проверка результата деплоя |
| `coder_post_edit.py` | После редактирования агентом 1c-coder | Вызов `get_errors` |
| `form_builder_post_create.py` | После создания формы | Проверка BOM, ID, дескриптора |
| `post_tool_audit.py` | После любого инструмента | Аудит операций |

## 10. Потоки данных: сценарии использования

### Сценарий A: Создание нового документа

```
Пользователь → Orchestrator
  → Фаза 0: backup + dump + КРИТИЧЕСКИЕ_ОШИБКИ.md
  → Фаза 1: Obsidian KG → MCP get_configuration_overview
  → Фаза 2: 1c-architect
      → MCP list_metadata_objects, get_connected_objects
      → Формирует ТЗ → [пользователь утверждает]
  → Фаза 2: 1c-coder (с ТЗ от architect)
      → MCP get_metadata_structure (связанные объекты)
      → Создаёт Documents/НовыйДок.xml + ObjectModule.bsl
      → Обновляет Configuration.xml + ConfigDumpInfo.xml
      → get_errors = 0
  → Фаза 2: 1c-form-builder
      → MCP get_form_structure
      → python _generate_form.py → Form.xml + Module.bsl
      → Обновляет ConfigDumpInfo.xml
  → Фаза 3: QC (get_errors всех файлов)
  → Фаза 4: 1c-deployer → validate → Full → мониторинг
  → Фаза 6: Obsidian KG update, Спецификация update
  → ДИАЛОГ next_action
```

### Сценарий B: Отладка runtime-ошибки

```
Пользователь: "При проведении документа ошибка"
  → Orchestrator → 1c-deployer
  → monitor -Action Check → найдена EXCP в ТЖ
  → [Ошибка не диагностируется за 2 попытки по логам]
  → Orchestrator: Фаза 5.5 — загрузить skill 1c-debug
  → ptm-debug: debug_connect
  → ptm-debug: debug_launch
  → ptm-debug: debug_set_breakpoints (ObjectModule.bsl, строка ОбработкаПроведения)
  → [Пользователь проводит документ в 1С — breakpoint срабатывает]
  → ptm-debug: debug_get_stack → стек вызовов
  → ptm-debug: debug_get_variables → найдена пустая ссылка
  → ptm-debug: debug_evaluate "Объект.Склад" → пусто!
  → Причина найдена → ptm-debug: debug_disconnect
  → 1c-coder → фикс BSL → get_errors = 0
  → 1c-deployer → validate → Full → мониторинг
```

## 13. Активация ptm-debug: что нужно сделать

### Шаг 1: Заполнить конфигурацию

Отредактировать `scripts/debug/debug_config.json`:
```json
{
  "platform": {
    "root": "C:\\Program Files\\1cv8\\8.3.27.XXXX"  ← актуальная версия
  },
  "infoBase": {
    "path": "D:\\Bases\\PTM"                          ← путь к ИБ
  }
}
```

### Шаг 2: Зарегистрировать MCP-сервер в VS Code

Добавить в `.vscode/mcp.json` (или `settings.json`):
```json
{
  "mcp": {
    "servers": {
      "ptm-debug": {
        "type": "stdio",
        "command": "python",
        "args": [
          "scripts/debug/debug_mcp_server.py",
          "--config", "scripts/debug/debug_config.json"
        ]
      }
    }
  }
}
```

### Шаг 3: Использование (workflow)

```
skill 1c-debug → debug_connect → debug_launch
→ debug_set_breakpoints { file_path: "...Module.bsl", lines: [42] }
→ [breakpoint срабатывает]
→ debug_get_stack → debug_get_variables → debug_evaluate
→ debug_continue / step_over / step_into
→ debug_disconnect
```
