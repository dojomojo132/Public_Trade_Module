## КАТЕГОРИЯ 1: Валидация XML конфигурации (P1 — используется ПОСТОЯННО)

### Что делает
Скрипт `validate-config.ps1` проверяет целостность XML-файлов 1С-конфигурации перед загрузкой:

1. **Configuration.xml ↔ файлы на диске** — каждый объект в `<ChildObjects>` должен иметь `.xml` файл
2. **ConfigDumpInfo.xml** — каждый объект должен иметь запись; UUID уникальны
3. **Структура XML объектов** — InternalInfo/GeneratedType, version="2.20", формат UUID
4. **Формы** — уникальность id элементов, наличие ContextMenu/ExtendedTooltip, незаменённые `{{placeholder}}`
5. **Перекрёстные ссылки** — RegisterRecords → реальные регистры, DefaultObjectForm → реальная форма
6. **Файловая структура** — Forms/*/Ext/Form.xml, Forms/*/Ext/Form/Module.bsl

### Файлы
| Файл | Строки | Действие |
|------|--------|----------|
| [validate-config.ps1](Документация/Валидация/validate-config.ps1) | 635 | Парсит Configuration.xml, ConfigDumpInfo.xml, все объектные XML, Form.xml |

### Как работает
Напрямую читает XML-файлы через `[xml]$configXml = Get-Content`, парсит с помощью XPath/XmlNamespaceManager, сверяет с файловой структурой через `Get-ChildItem`, `Test-Path`.

### Можно ли заменить MCP?
**Частично.** Проверки 1-3 (метаданные, списки объектов) MCP уже даёт через `list_metadata_objects` + `get_metadata_structure`. Но:
- Проверка **соответствия XML-файлов на диске** — MCP не видит диск, нужен доступ к файловой системе
- Проверка **форм** (id, вложенные элементы) — `get_form_structure` даёт только метаданные, не XML-структуру
- Проверка **ConfigDumpInfo.xml** — MCP не знает о CDI  
- Проверка **перекрёстных ссылок** — теоретически можно через `execute_query` + `execute_code`

### Предложение MCP-инструмента

**Инструмент: `validate_configuration`** (P1)

```
Параметры:
  scope: string = "All" | "Metadata" | "Forms" | "CrossRefs"
  
Возвращает:
  - Список ошибок: несоответствия Configuration.xml ↔ ИБ
  - Несоответствия ConfigDumpInfo ↔ реальные объекты
  - Отсутствующие InternalInfo/GeneratedType
  - Дублирующиеся UUID
  
Ценность: Проверка из ИБ — "единственный источник истины" vs файлы на диске.
```

**Реальность:** Этот инструмент **НЕ заменит** validate-config.ps1 полностью, т.к. задача скрипта — проверить файлы ДО загрузки (pre-deploy), а MCP работает с уже загруженной конфигурацией. Скрипт критически нужен как gate-keeper перед деплоем.

## КАТЕГОРИЯ 2: Статический анализ BSL (P2)

### Что делает
Два инструмента анализируют BSL-код на антипаттерны:

1. **`_ptm_analyze.py`** — Python regex-анализатор, ищет:
   - `ТекущаяДата()` → `ТекущаяДатаСеанса()`
   - `ПоказатьВопрос()` → `ВопросАсинх()`
   - `Сообщить()` без привязки к полям
   - `ЭтаФорма` → `ЭтотОбъект`
   - `ИмяПользователя() + НайтиПоНаименованию`
   - `Предупреждение()`, `Вопрос()`, `Найти()`

2. **`run-tests.ps1 -Action BslAnalysis`** — запуск BSL Language Server (Java) для полного статического анализа

### Файлы
| Файл | Строки | Действие |
|------|--------|----------|
| [_ptm_analyze.py](_ptm_analyze.py) | 304 | `rglob("*.bsl")`, regex-поиск антипаттернов |
| [run-tests.ps1](Документация/Тестирование/run-tests.ps1) | 591 | Запуск BSL LS через `java -jar bsl-language-server.jar --analyze` |

### Можно ли заменить MCP?
**Частично.** 

- `_ptm_analyze.py` можно заменить MCP-инструментом `execute_code`, который выполнит аналогичный regex-анализ из BSL. Но проблема: в BSL нет доступа к тексту модулей через `МетаданныеОбъекта.ПолучитьТекстМодуля()` из расширения в safe mode.
- BSL Language Server — внешний инструмент, MCP его не заменит.

### Предложение MCP-инструмента

**Инструмент: `analyze_bsl_patterns`** (P2)

```
Параметры:
  metaType: string = "Documents" | "Catalogs" | "CommonModules" | "All"
  name: string (опционально — конкретный объект)
  patterns: string[] = ["ТекущаяДата", "Сообщить", "ЭтаФорма", ...]

Возвращает:
  - Список найденных антипаттернов: модуль, строка, паттерн, рекомендация
  
Реализация: Через Метаданные[тип].ПолучитьТекстМодуля() + regex в BSL
Проблема: safe mode расширения может блокировать ПолучитьТекстМодуля()
```

**Альтернатива:** Оставить `_ptm_analyze.py` как есть — он работает с файлами на диске, что является правильным подходом для pre-deploy проверки.

## КАТЕГОРИЯ 3: Мониторинг ошибок ТЖ+ЖР (P1)

### Что делает
`monitor-errors.ps1` — двухисточниковый мониторинг ошибок runtime:

1. **Технологический журнал (ТЖ)** — чтение EXCP-событий из .log файлов (требует настройки logcfg.xml)
2. **Журнал регистрации (ЖР)** — чтение ошибок из .lgp файлов базы

### Файлы
| Файл | Строки | Действие |
|------|--------|----------|
| [monitor-errors.ps1](Документация/Валидация/monitor-errors.ps1) | 635 | Чтение ТЖ (.log) + ЖР (.lgp), парсинг, структурированный вывод |
| [_run_monitor.py](scripts/_run_monitor.py) | 15 | Обёртка для запуска через Python |

### Уже реализовано в MCP
**`get_event_log`** — чтение ЖР через `ВыгрузитьЖурналРегистрации()`. Заменяет часть ЖР.

### Что НЕ заменено (исторически)
- **Настройка ТЖ** (logcfg.xml) — Setup/Stop работают через MCP (расширение пишет logcfg.xml напрямую)
- **Фильтрация по processName** - реализована (фильтрует по "Public Trade Module")

### Предложение MCP-инструмента

**Инструмент: `get_tech_journal`** (✅ РЕАЛИЗОВАН, 26.02.2026)

```
Параметры:
  action: "Setup" | "Stop" | "Status" | "Check" (обяз.)
  lastMinutes: number = 30   (action=Check)
  maxRows: number = 50       (action=Check)
  eventFilter: "EXCP" | "SDBL" | "CALL" | "SCALL" | "CONN"
  
Решение: расширение 1С читает .log-файлы через КопироватьФайл() во временный,
затем парсит и фильтрует по processName/типу/времени.

Статус: работает. Развёрнуто 2 EXCP-ошибки на тестовой сессии.
```

**Рекомендация:** Оба источника ошибок теперь доступны через MCP:
- **ЖР (Журнал регистрации):** `get_event_log` — ошибки уровня приложения  
- **ТЖ (Технологический журнал):** `get_tech_journal` (action=Check) — runtime EXCP/SDBL/CALL  
- **monitor-errors.ps1** — резервный вариант при отсутствии MCP-подключения

### Можно ли заменить MCP?
**НЕТ.** Это CLI-операции с 1cv8.exe (DESIGNER режим), которые:
- Загружают XML в ИБ (файловая операция → ИБ)

#### 1. `validate_metadata_integrity` (P1)
**Замещает:** Часть `validate-config.ps1` — проверка с точки зрения ИБ (post-deploy)

```
Параметры:

Возвращает:

  - Формы объектов → реально открываются или нет
  - Несоответствия между объявленными и реальными данными

Реализация BSL:
  Для каждого Документ из Метаданные.Документы:
    Движения = Документ.Движения
    Для каждого Регистр из Движения:
      // Проверить что регистр существует
    КонецЦикла
    // Проверить DefaultObjectForm
    // Проверить что формы открываются
  КонецЦикла

Ценность: Позволяет агенту проверить целостность ПОСЛЕ деплоя из MCP
(validate-config.ps1 проверяет ПЕРЕД деплоем из файлов)
```

#### 2. `get_configuration_stats` (P1)

Реализация BSL:

Ценность: Одним вызовом получает "обзор конфигурации" вместо 10+ вызовов

**Замещает:** `find_references` + анализ реквизитов типов
