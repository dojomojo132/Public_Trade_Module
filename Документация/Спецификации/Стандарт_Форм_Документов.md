# ТЗ: Стандарт форм документов PTM

> **Статус:** Проектирование
> **Дата:** 2026-05-22
> **Архитектура:** Гибрид (декларативный конфиг + Svelte slots/snippets)

---

## 1. Цель

Унифицировать поведение и UX **всех** документов системы (приходная/расходная накладная, перемещение, инвентаризация, списание, возврат, платёжные документы и будущие), чтобы:

1. Стандартные UX-паттерны (grid-навигация, Tab, Ins/Del, Ctrl+S, dirty-индикатор, read-only после проведения) реализовывались **один раз** в движке формы.
2. Конкретный документ описывал только то, что у него уникально (поля шапки, колонки ТЧ, формулы, проверки).
3. Возможность расширения без правки движка через slots/snippets.

## 3. Конфиг документа (DocumentConfig)

### 3.1 Минимальный пример (Приходная накладная)

```typescript
import { defineDocument, type DocumentConfig } from '$lib/document/types';

export const invoiceInConfig: DocumentConfig = defineDocument({
  type: 'invoice_in',
  title: 'Приходная накладная',
  pluralTitle: 'Приходные накладные',
  icon: '📥',

  // Поля шапки
  headerFields: [
    { name: 'warehouseId', label: 'Склад', kind: 'ref', refType: 'warehouse', required: true, tabOrder: 1 },
    { name: 'counterpartyId', label: 'Контрагент', kind: 'ref', refType: 'counterparty', tabOrder: 2 },
    { name: 'comment', label: 'Комментарий', kind: 'string', tabOrder: 3 },
  ],

  // Колонки табличной части
  lineColumns: [
    { name: 'product', label: 'Товар', kind: 'ref', refType: 'product', width: '40%', required: true, navCol: 0 },
    { name: 'qty', label: 'Кол-во', kind: 'number', align: 'right', min: 0.001, navCol: 1 },
    { name: 'price', label: 'Цена', kind: 'number', align: 'right', min: 0, navCol: 2 },
    { name: 'sum', label: 'Сумма', kind: 'number', align: 'right', calc: (l) => l.qty * l.price, navCol: 3 },
    { name: 'priceExcl', label: 'Цена б/НДС', kind: 'number', align: 'right', calc: (l) => l.price / 1.2, navCol: 4 },
    { name: 'sumExcl', label: 'Сумма б/НДС', kind: 'number', align: 'right', calc: (l) => l.sum / 1.2, navCol: 5 },
  ],

  // Footer / итоги
  totals: [
    { label: 'Всего к оплате', calc: (doc) => doc.lines.reduce((s, l) => s + l.sum, 0), format: 'money' },
  ],

  // Проверки перед сохранением (черновика)
  validateDraft: (doc) => {
    if (!doc.warehouseId) return 'Выберите склад';
    return null;
  },

  // Дополнительные проверки перед проведением
  validatePost: (doc) => {
    if (doc.lines.length === 0) return 'Добавьте хотя бы одну строку';
    if (doc.lines.some(l => !l.product || l.qty <= 0)) return 'Все строки должны иметь товар и кол-во > 0';
    return null;
  },

  // API endpoints (опционально, иначе по умолчанию /api/documents)
  api: {
    create: 'POST /api/documents',
    update: 'PUT /api/documents/:id',
    get: 'GET /api/documents/:id',
    post: 'POST /api/documents/:id/post',
    list: 'GET /api/documents?doc_type=invoice_in',
  },
});
```

## 4. Стандартное поведение (зафиксировано)

### 4.1 Навигация по табличной части

| Клавиша | В режиме навигации (nav) | В режиме редактирования (edit) |
|---------|--------------------------|-------------------------------|
| `↑` `↓` | Перейти на строку выше/ниже | Выйти из редактирования + перейти |
| `←` `→` | Перейти на колонку левее/правее | Выйти при курсоре на краю строки |
| `Enter` | Войти в редактирование | Выйти. Если последняя строка — следующая ячейка |
| `F2` | Войти в редактирование | (нет) |
| `Esc` | (нет) | Выйти из редактирования |
| `Ins` | Добавить новую строку ниже | — |
| `Del` | Запросить удаление строки | — |
| `Ctrl+Del` | Удалить строку без вопроса | — |
| Цифры | Войти в редактирование с этой цифрой | Обычный ввод |

### 4.2 Шапка

| Клавиша | Действие |
|---------|----------|
| `Tab` | Следующее поле по `tabOrder`, после последнего → первая строка ТЧ |
| `Shift+Tab` | Предыдущее поле |
| `Enter` | Следующее поле (если поле не multiline) |

### 4.3 Глобальные горячие клавиши формы

| Клавиша | Действие |
|---------|----------|
| `Ctrl+S` | Сохранить черновик |
| `Ctrl+Enter` | Сохранить и провести |
| `Esc` | Закрыть форму (с подтверждением если dirty) |
| `Ctrl+P` | Печать (если есть шаблон) |

### 4.4 Визуальные индикаторы

- **Заголовок:** `Приходная накладная №123 от 22.05.2026 *` (звёздочка = dirty)
- **Активная ячейка:** `ring-1 ring-brand-500` без фона
- **Редактируемая ячейка:** `bg-slate-700` + ring
- **Проведённый документ:** read-only, кнопка "✎ Редактировать" → пользователь сам снимает блокировку (только для непроведённых) или отменяет проведение
- **Ошибки валидации:** красный ring + tooltip с текстом

### 4.5 Сохранение

- Кнопка "Сохранить черновик" → `POST` / `PUT`, остаётся на форме
- Кнопка "Сохранить и провести" → `PUT` + `POST /post`, переход на просмотр
- Автосохранение черновика — **по умолчанию выключено**, опционально через `config.autosave: 30` (сек)

### 4.6 Поведение проведённого документа

- Все поля read-only
- Кнопки видимые: "Отменить проведение", "Копировать", "Печать", "← К списку"
- Скрытые: "Сохранить", "Провести"

## 7. Статусы документа и регистры (закрыто Q1)

### 7.1 Жизненный цикл документа

В системе **нет** концепции «проведения» 1С. Документ влияет на остатки сразу после сохранения, если его статус это позволяет.

Поле в таблице `documents`:

```sql
status: enum('active', 'excluded', 'deleted')  -- default 'active'
```

| Статус | Описание | Виден в списках | Влияет на остатки |
|---|---|---|---|
| `active` | Обычное рабочее состояние | да | **да** |
| `excluded` | Временно исключён из расчётов (например, спорный документ) | да, с бейджем | нет |
| `deleted` | Логически удалён (soft delete) | нет (опц. фильтр «Удалённые») | нет |

**Переходы:**
- `active` ↔ `excluded` — кнопка «Исключить из движений» / «Вернуть в движения» в тулбаре.
- `active` / `excluded` → `deleted` — кнопка «Удалить».
- `deleted` → `active` — кнопка «Восстановить» (в списке удалённых).

Изменение статуса = пересчёт затронутых снапшотов регистров.

### 7.2 Регистры (источник истины для остатков/оборотов)

Регистры — отдельные таблицы, аналог регистров накопления 1С. Документ при сохранении пишет движения, при смене статуса/правке — переписывает их.

Структура регистра описывается схемой:

```ts
interface RegisterSchema {
  name: string;                   // 'StockBalance'
  kind: 'balance' | 'turnover';   // остатки | обороты
  dimensions: Dimension[];        // ['warehouseId', 'productId', 'batchId', ...]
  resources: Resource[];          // ['quantity', 'amount']
  snapshot: SnapshotConfig;       // см. 7.3
}
```

### 7.3 Снапшоты регистров

Снапшоты ускоряют чтение остатков на произвольный момент. Формула:

```
balance(grain, T) = snapshot(grain, T0) + Σ movements(grain, T0 < t ≤ T)
```
где `T0` — ближайший снапшот разреза `grain` до момента `T`.

```ts
interface SnapshotConfig {
  /** Подмножество измерений регистра, по которым делается срез.
   *  Меньше измерений → меньше строк, но грубее агрегация. */
  grain: string[];                // например ['warehouseId', 'productId']

  /** Периодичность фиксации снапшота. */
  period: 'day' | 'week' | 'month';
}
```

**Принцип пересчёта:** при правке/смене статуса документа задним числом пересчитываются только снапшоты затронутого разреза (`grain` со значениями измерений этого документа), начиная с периода, в котором лежит дата изменения. Остальные разрезы не трогаем.

### 7.4 Отражение в UI

- Бейдж статуса в шапке формы (`active` — без бейджа, `excluded` — жёлтый, `deleted` — серый).
- Тулбар: кнопка-переключатель статуса (`active`/`excluded`).
- В режиме `excluded`/`deleted` форма по умолчанию read-only (включается «Редактировать» как для активного).
- Вкладка «Движения» в режиме просмотра — список записей регистров, созданных этим документом.

## 7a. Описание движений документа (закрыто Q2)

### 7a.1 Где описывать

Движения описываются **в TS-конфиге документа** в секции `movements`. Конфиг — единый источник для UI и backend.

```ts
interface DocumentMovementsSpec {
  /** Декларативные правила: mapping строки ТЧ → запись регистра.
   *  Сериализуются в JSON, валидируются и в UI, и в Rust. */
  rules: MovementRule[];

  /** Опционально: TS-функция для случаев, где декларации недостаточно
   *  (агрегации, условные ветки, расчёт из шапки + ТЧ).
   *  Выполняется только в UI. */
  compute?: (doc: DocumentSnapshot) => Movement[];
}

interface MovementRule {
  register: string;                       // 'StockBalance'
  source: 'header' | 'lines';             // откуда берём данные
  when?: string;                          // JSON-логика (опц.), например {'!=': [{'var': 'qty'}, 0]}
  dimensions: Record<string, FieldRef>;   // { warehouseId: 'header.warehouseId', productId: 'line.productId' }
  resources:  Record<string, FieldRef>;   // { quantity: 'line.qty', amount: 'line.total' }
  sign: '+' | '-';                        // приход / расход
}

type FieldRef = string;  // путь: 'header.xxx' | 'line.xxx' | литерал/выражение JSON-Logic
```

### 7a.2 Поток данных при сохранении

```
UI:
  1. Прогоняет rules локально → movementsFromRules
  2. Если есть compute() → movementsFromCompute (заменяет/дополняет)
  3. Финальный movements[] показывается на вкладке «Движения» (preview)
  4. POST/PUT /api/documents/{id} { document, lines, movements }

Rust:
  1. Загружает конфиг документа (тот же source-of-truth — JSON-экспорт TS-конфига)
  2. Прогоняет rules сам → movementsExpected
  3. Если compute отсутствует:
       assert movements == movementsExpected
  4. Если compute есть:
       валидирует movements по правилам:
         - все register допустимы для типа документа
         - все dimensions/resources имеют корректные типы
         - суммы по ресурсам не противоречат totals документа
         - sign соответствует допустимым для register
  5. Запись в таблицы регистров в одной транзакции с документом
  6. Триггерит пересчёт затронутых снапшотов (см. 7.3)
```

### 7a.3 Защита от подделки movements[] клиентом

- Если конфиг **не имеет** `compute` — Rust **пересчитывает** movements сам и игнорирует присланные (или сравнивает и отклоняет при расхождении).
- Если `compute` **есть** — Rust валидирует структуру и инварианты, но доверяет конкретным значениям. Конфигурация с `compute` помечается как «требует доверенного клиента» (RBAC может ограничивать таких пользователей).
- Любая ошибка валидации → откат транзакции, документ не сохраняется.

### 7a.4 Хранение конфига для backend

TS-конфиг при сборке экспортируется в JSON (только `rules` — функции не сериализуются) и кладётся в `ptm-server/configs/documents/<type>.json`. Rust читает на старте + hot-reload по сигналу.

## 7c. Подбор товаров (закрыто Q4)

В ячейке колонки `ref` всегда работает **inline-поиск** (как сейчас в накладной). Дополнительно в тулбаре ТЧ предусмотрена кнопка **«Подбор»**, открывающая модальный диалог множественного выбора.

```ts
interface RefColumn {
  kind: 'ref';
  refType: string;                // 'Product'
  picker?: {
    enabled: boolean;             // default false — кнопка не показывается
    component?: string;           // имя кастомного компонента подбора (опц.)
    multi?: boolean;              // выбор нескольких (default true)
  };
}
```

Поведение по умолчанию (без `picker.component`) — стандартный диалог со списком, фильтром, чекбоксами; на «Готово» добавляет выбранные позиции как новые строки ТЧ (используя `defaults` колонок). Кастомный компонент — для специализированных подборов (по штрихкодам, по остаткам склада и т. п.).

## 7d. Версионирование конфигов (закрыто Q5)

**MVP:** конфиги хранятся в репозитории (git), отдельного `configVersion` нет. Версия = версия приложения. Несовместимые изменения конфига решаются разовыми миграциями данных в БД, сопровождающими релиз.

Будущее расширение (когда появится реальная боль): поле `configVersion: number` в конфиге + `configVersion` у документа в БД + блокировка пересохранения при расхождении (вариант b в обсуждении Q5). Архитектура движка изначально оставляет место под это поле, чтобы добавить без переделок.

## 8. Что НЕ входит в стандарт (явно за скобками)

- Отчёты СКД (своя архитектура)
- Кассовая смена (специфический workflow)
- Драйверы оборудования (отдельные плагины)
