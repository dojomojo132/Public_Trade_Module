### 1.2 Корневая проблема: монолит в горячем контексте

`copilot-instructions.md` (~2000 строк) загружается в контекст **КАЖДОГО** запроса — даже для "переименуй переменную". Из этих ~2000 строк:

| Система диалогов (3 типа) | ~100 | ✅ Да | — |
| Каталог MCP (40+ инструментов) | ~400 | ⚠️ Частично | metadata-check skill |
| Алгоритм разработки (фазы 0–5) | ~300 | ❌ Нет | deploy skill, prompts |
| Негативный словарь BSL | ~100 | ❌ Нет | bsl.instructions, bsl-review skill |
| Правила XML | ~150 | ❌ Нет | xml-1c.instructions, form-gen skill |
| Структура файлов проекта | ~200 | ⚠️ Частично | — |
| Правила форм и ID | ~150 | ❌ Нет | form-gen skill |
| Multi-file чеклист | ~100 | ❌ Нет | xml-1c.instructions, prompts |
| PowerShell + кириллица | ~100 | ⚠️ Частично | — |
| Деплой и оптимизация | ~150 | ❌ Нет | deploy skill |

**Вывод:** из ~2000 строк монолита только ~350–450 строк уникальны. Остальные ~1500 дублируют то, что уже есть в skills/instructions. Все ~2000 строк загружаются всегда, раздувая контекст.

### 1.4 Нет модели активации

Сейчас нет осознанного решения "когда что загружается":

- `copilot-instructions.md` загружается всегда → должен быть минимальным
- `instructions/` загружаются при редактировании файлов по маске → хорошо для правил файлов
- `skills/` загружаются при совпадении описания с намерением → хорошо для процедур
- `agents/` загружаются при явном вызове → хорошо для ролевых профилей
- `prompts/` загружаются при явном вызове пользователем → хорошо для шаблонов

Но поскольку copilot-instructions уже содержит ВСЁ, skills и instructions становятся избыточным дублированием, а не дополнением.

### 1.5 Два каталога промптов

| Каталог | Конвенция | Файлы |
|---------|-----------|-------|
| `.github/prompts/` | Workflow-уровень (new-task, fix-deploy, review) | 3 файла |
| `.github/copilot-prompts/` | Action-уровень (create-catalog, create-form) | 5 файлов |

Нет документированной конвенции, куда класть новый промпт.

### 1.6 Нет алгоритма добавления

Когда появляется новый инструмент (MCP-tool, PowerShell-скрипт, Python-утилита), нет ответа на вопросы:
- В какой файл добавить описание?
- Нужно ли обновлять copilot-instructions.md?
- Создавать ли новый skill?
- Как не создать дубликат?

## 2. Целевая архитектура

### 2.1 Принцип: Single Source of Truth Per Rule

Каждое правило/процедура/справочник живёт **ровно в одном файле**. Другие файлы могут **ссылаться** на него, но не дублировать.

### 2.2 Модель слоёв

```
Слой 0: copilot-instructions.md (ВСЕГДА в контексте — включая субагентов!)
│       ├── Идентичность (роль, платформа)
│       ├── Топ-правила (5–7 абсолютных запретов/обязательств)
│       ├── Система диалогов (ДИАЛОГ 1/2/3) — для ВСЕХ агентов
│       ├── Навигационная карта (какой файл за что отвечает)
│       └── Краткая таблица MCP-инструментов (имя → описание, без параметров)
│       ⚠️ НЕ содержит: процедуры (→ skills), подробные правила BSL/XML (→ instructions)
│       Целевой размер: 300–350 строк (сейчас ~2000)
│
Слой 1: instructions/*.instructions.md (авто-загрузка по маске файла)
│       ├── bsl.instructions.md → applyTo: **/*.bsl
│       ├── xml-1c.instructions.md → applyTo: **/*.xml
│       └── (будущее: ps1.instructions.md, py.instructions.md)
│       Ответственность: ВСЁ что связано с конкретным типом файла
│       (синтаксис, стиль, И процедуры специфичные для этого типа)
│
Слой 2: skills/*/SKILL.md (on-demand по описанию)
│       ├── 1c-deploy → процедура деплоя
│       ├── 1c-form-generator → создание форм
│       ├── 1c-bsl-review → ревью кода
│       ├── 1c-metadata-check → MCP-верификация (полный каталог MCP)
│       ├── (будущее: 1c-report → создание отчётов)
│       └── (будущее: 1c-debug → отладка RDBG)
│       Ответственность: ПРОЦЕДУРЫ (многошаговые алгоритмы)
│
Слой 3: agents/*.agent.md (при явном вызове агента)
│       ├── orchestrator → координация, декомпозиция, контроль качества
│       ├── 1c-architect → проектирование, архитектурный контроль
│       ├── 1c-form-builder → XML-формы
│       ├── 1c-coder → BSL-код (модули, обработчики, проведение)
│       ├── 1c-deployer → деплой, диагностика, маршрутизация ошибок
│       └── Explore → исследование кодовой базы (встроенный, только чтение)
│       Ответственность: РОЛЕВЫЕ ПРОФИЛИ + workflow-механики
│       Не дублируют процедуры — ссылаются на skills
│
Слой 4: prompts/*.prompt.md (при явном вызове пользователем)
│       └── Шаблоны повторяемых сценариев (new-task, fix-deploy, review, create-*)
│       Ответственность: ШАБЛОНЫ ЗАПУСКА (параметры + ссылки на skills)
│       Не дублируют процедуры
│
Слой 5: hooks/ (автоматическая инжекция)
│       └── guardrails (лёгкие напоминания при старте/редактировании)
│       Ответственность: ПАССИВНАЯ БЕЗОПАСНОСТЬ (не блокируют, напоминают)
```

### 2.2а Мультиагентная модель (5 специализированных агентов + Explore)

```
User → orchestrator (координация + диалоги)
         │
         ├── 1c-architect (проектирование)
         │     Читает: спецификацию, MCP, структуру конфигурации
         │     Выдаёт: ТЗ (объекты, реквизиты, типы, связи, регистры)
         │     Правило: ТЗ ОБЯЗАТЕЛЬНО утверждается пользователем
         │     Skills: 1c-metadata-check
         │
         ├── 1c-form-builder (XML-формы)
         │     Получает: ТЗ от architect (элементы, layout, datapath)
         │     Делает: Form.xml, descriptor, привязки к объекту
         │     Skills: 1c-form-generator
         │     Instructions: xml-1c.instructions.md (авто)
         │
         ├── 1c-coder (BSL-код)
         │     Получает: ТЗ от architect (какая логика нужна)
         │     Делает: модули объектов, обработчики форм, проведение
         │     Skills: 1c-bsl-review
         │     Instructions: bsl.instructions.md (авто)
         │
         ├── 1c-deployer (деплой + диагностика)
         │     Делает: деплой, мониторинг, отладка
         │     Маршрутизирует ошибки: XML → form-builder, BSL → coder
         │     Skills: 1c-deploy, 1c-debug
         │
         └── Explore (исследование)
               Только чтение / поиск (встроенный агент)
```

**Принцип утверждения:** ТЗ от 1c-architect **ВСЕГДА** представляется пользователю на утверждение / корректировку
перед передачей в работу другим агентам. Никакая реализация не начинается
без явного подтверждения пользователем.

### 2.2б Ростер агентов (подробно)

| Агент | Роль | Tools | Skills | Instructions |
|---|---|---|---|---|
| **orchestrator** | Координация, декомпозиция, QC, диалоги | read, search, execute, agent, todo | — | — |
| **1c-architect** | Проектирование, архитектурный контроль | read, search | 1c-metadata-check | — |
| **1c-form-builder** | XML-формы (Form.xml, descriptor, layout) | read, search, edit, execute | 1c-form-generator | xml-1c.instructions |
| **1c-coder** | BSL-код (модули, обработчики, проведение, XML объектов) | read, search, edit, execute, todo | 1c-bsl-review | bsl.instructions, xml-1c.instructions |
| **1c-deployer** | Деплой, мониторинг, отладка, маршрутизация ошибок | read, search, edit, execute, agent | 1c-deploy, 1c-debug | — |
| **Explore** | Исследование кодовой базы | read, search | — | — |

**Почему узкая специализация:**
- Каждый агент знает свою область глубоко, а не всё поверхностно
- Минимальный контекст — каждый грузит только свои skills/instructions
- Ошибки маршрутизируются к правильному специалисту
- Новые агенты добавляются без изменения существующих

### 2.2в Типовые сценарии взаимодействия

**Сценарий 1: Создание нового объекта (сложная задача)**
```
orchestrator:
  1. → 1c-architect: "Спроектируй документ РасходТовара"
     ← ТЗ: реквизиты, типы, ТЧ, регистры, формы
  2. orchestrator → ПОЛЬЗОВАТЕЛЬ: "Утвердите ТЗ"
     (пользователь корректирует или утверждает)
  3. → 1c-coder: "Создай XML объекта + ObjectModule.bsl по этому ТЗ"
  4. → 1c-form-builder: "Создай форму документа по этому ТЗ"
  5. → 1c-deployer: "Деплой"
     ← Если ошибка XML → 1c-deployer → 1c-form-builder
     ← Если ошибка BSL → 1c-deployer → 1c-coder
  6. Мониторинг → ДИАЛОГ
```

**Сценарий 2: Исправление ошибки (простая задача)**
```
User → 1c-coder напрямую: "Поправь баг в модуле проведения"
(без orchestrator, без architect)
```

**Сценарий 3: Маршрутизация ошибок деплоя**
```
1c-deployer:
  deploy → ОШИБКА
  │
  ├─ Ошибка в Form.xml / XML-структуре → вызвать 1c-form-builder
  ├─ Ошибка в BSL {Модуль(строка)} → вызвать 1c-coder
  ├─ EXIT_CODE -2 (таймаут) → ОТКАТ → сообщить orchestrator
  └─ EXIT_CODE 10 (бэкап) → сообщить orchestrator
```

### 2.2г Контекст при мультиагентных вызовах

**Критично:** `copilot-instructions.md` загружается не только в основной разговор,
но и в КАЖДЫЙ вызов субагента через `runSubagent`. Поэтому его размер влияет
мультипликативно — 5 вызовов субагентов = 5× загрузка монолита.

```
User → orchestrator (контекст A)
         │
         ├── runSubagent("Explore", prompt)
         │     Контекст B: copilot-instructions.md + prompt
         │     Возвращает: только текстовый результат → в A (компактно)
         │
         ├── runSubagent("1c-architect", prompt)
         │     Контекст C: copilot-instructions.md + 1c-architect.agent.md
         │                 + skills (1c-metadata-check on-demand)
         │     Возвращает: ТЗ (текст) → в A → пользователю на утверждение
         │
         ├── runSubagent("1c-coder", prompt + утверждённое ТЗ)
         │     Контекст D: copilot-instructions.md + 1c-coder.agent.md
         │                 + bsl.instructions.md (авто) + xml-1c.instructions.md (авто)
         │                 + skills (1c-bsl-review on-demand)
         │     Возвращает: текстовый результат → в A
         │
         ├── runSubagent("1c-form-builder", prompt + утверждённое ТЗ)
         │     Контекст E: copilot-instructions.md + 1c-form-builder.agent.md
         │                 + xml-1c.instructions.md (авто) + skill (1c-form-generator)
         │     Возвращает: текстовый результат → в A
         │
         └── Контекст A остаётся ЧИСТЫМ
             (содержит только промпты + результаты, не внутренние tool-вызовы)
```

**Выводы для архитектуры:**
- Тонкий copilot-instructions.md экономит контекст в каждом субагенте
- Субагенты изолированы — их внутренняя работа не засоряет основной контекст
- Диалоги (ДИАЛОГ 1/2/3) остаются в copilot-instructions.md — они нужны ВСЕМ агентам
- Полный MCP-каталог нужен только при работе с метаданными → переносим в skill

## 3. Алгоритм добавления нового инструмента

### 3.1 Блок-схема принятия решения

```
Новый инструмент / правило / процедура
    │
    ▼
(1) Это правило синтаксиса/стиля для конкретного типа файла?
    │   ДА → Добавить в существующий instructions/*.instructions.md
    │         Если нет подходящего → создать новый (applyTo: маска)
    │         ⚠️ НЕ дублировать в copilot-instructions.md
    │
    НЕТ
    │
    ▼
(2) Это многошаговая процедура (деплой, генерация, ревью)?
    │   ДА → Добавить в существующий skill или создать новый
    │         Если расширение существующего → обновить SKILL.md
    │         Если новая область → создать skills/<name>/SKILL.md
    │         ⚠️ НЕ дублировать в copilot-instructions.md
    │
    НЕТ
    │
    ▼
(3) Это новая роль / способ работы агента?
    │   ДА → Обновить существующий agent или создать новый
    │         Процедуры вынести в skill, в агенте — только ссылка
    │         ⚠️ НЕ дублировать процедуры в агенте
    │
    НЕТ
    │
    ▼
(4) Это повторяемый пользовательский сценарий?
    │   ДА → Создать prompt в prompts/
    │         Шаблон параметров + ссылки на skills
    │         ⚠️ НЕ дублировать процедуры в промпте
    │
    НЕТ
    │
    ▼
(5) Это абсолютное правило / навигация / identity?
    │   ДА → Добавить в copilot-instructions.md
    │         ⚠️ Максимум 5–10 строк на одно правило
    │
    НЕТ
    │
    ▼
(6) Это пассивная проверка безопасности?
        ДА → Добавить в hooks/
```

### 3.2 Чеклист перед добавлением

```
□ 1. Проверить: нет ли этого уже в существующем файле?
      → grep по всем .md в .github/ на ключевые слова
□ 2. Определить слой по блок-схеме (раздел 3.1)
□ 3. Определить файл-владелец
□ 4. Добавить контент ТОЛЬКО в файл-владелец
□ 5. Если нужна навигация → добавить 1 строку в copilot-instructions.md (навигационная карта)
□ 6. НЕ дублировать в copilot-instructions.md или других файлах
□ 7. Проверить: copilot-instructions.md НЕ вырос (если вырос — контент не туда)
```
